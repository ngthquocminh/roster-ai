## 4. Gate B — the central finding

### The dataset floor, precisely measured

`backend/evals/golden/` holds 30 cases against `epics.md:1620`'s 50-case floor. Also short:
consequential+prohibited cases (9 of the required ≥10) and the `demonstration` capability (2 of the
required ≥4, if it counts as an "allowed capability" under NFR28 — not settled here).
`epics.md:1627`'s caveat permits lowering the floor only with a recorded rationale, "never pad the
dataset to reach it."

### The dataset is a legitimate golden dataset by construction

Verified against the general LLM-eval concept (ground truth authored independent of the model,
versioned, deterministic to run, evaluator-bound, risk-weighted): every case carries
`case_version`, `capability`, `risk_class`, `expected_outcome`, `expected_tool_calls`; three
evaluators (`ToolRoutingEvaluator`, `GroundingEvaluator`, `PolicyOutcomeEvaluator`) bind to it; it
includes adversarial/injection cases. The gap is coverage, not concept.

### The live-eval mechanism existed but had never actually run

`test_golden_cases_against_live_agent_are_non_authoritative` (`backend/tests/test_evaluation_harness.py`)
is the project's only mechanism for checking the golden dataset against a real provider — gated
`@pytest.mark.live`, excluded by default, never authoritative for release by design (epics.md's
"Deterministic-first CI" gate). Found, this session, to have three independent defects that meant
it had never actually completed a real run:

1. **No real assertion.** It only asserted `verdict.authoritative is False`, which is a constant for
   `run_source="live"` — the test passed regardless of whether the live model routed correctly.
2. **Would crash, not run.** `models.ALLOW_MODEL_REQUESTS = False` is set at module scope
   (`test_evaluation_harness.py:73`) and was never overridden for the live test, so pydantic-ai's
   `check_allow_model_requests()` would raise `RuntimeError` on the first real call.
3. **No tools, no deps.** It built the runtime via `create_agent_runtime(settings=...)` alone —
   `capabilities=()` by default — bypassing `_runtime_for_case`'s per-case capability/deps/
   answer-type wiring that every other case-driving path in this codebase uses. Even past defects
   1–2, the agent would have had zero tools to call.

**Fixed this session** (`backend/evals/report.py`, `backend/tests/test_evaluation_harness.py`):
extracted the routing+grounding+policy scoring shared by the authoritative double run into
`_evaluate_case`, added an optional `model` override to `runtime_for_modules`/`_runtime_for_case` so
a live model reuses the exact same capability/deps/answer-type wiring, wrapped the live test in
`models.override_allow_model_requests(True)`, and made it assert and report real per-case failures.
Verified: 123 pre-existing tests still pass (`test_evaluation_harness.py`,
`test_capability_conformance.py`, `test_agent_runtime_adapter.py`) — the refactor changed no
deterministic-path behavior.

### The measured result

Ran all 30 golden cases live against two providers:

| Model | Passed | Failed |
|---|---|---|
| `anthropic:claude-haiku-4-5-20251001` | 3/30 | 27/30 |
| `anthropic:claude-sonnet-5` | 3/30 | 27/30 |

**Identical passing set for both models** — `demonstration-repeat-once`,
`demonstration-repeat-with-approval`, `scheduling-inspect-refuse-unsupported-request` (all
zero-tool-call cases). **Identical failing set.** A flagship model performs no better than a
cheap/fast one on this bar, ruling out model capability as the explanatory variable.

Failure shape, both models: 13 cases with no tool call at all where one was expected; 9 cases where
the right tool was called the right number of times but literal arguments differed (several of
these expect fixture-internal constants — e.g. `task_id:"pick", start_minute:2880, end_minute:4320`
— that the case's own prompt text never states, so no model could infer them from the prompt alone);
2 under-called; 3 over-called.

### The decision

Minh's position, correcting the facilitator's initial framing: the dataset exists to be passed, and
low pass rate is the system's problem to fix (tool descriptions, prompts, or genuinely-wrong case
expectations), not something to disclose away as an inherent evaluator-strictness artifact. Sizing
the fix — diagnosing all 27 failures individually, correcting tool descriptions/prompts and/or
rewriting cases whose expected arguments are unreachable from their own prompt text, then
re-verifying — is real work, comparable in shape to an Epic 5 story (Facts/Decisions/ACs,
demonstrated-red, review), not a retrospective-session patch.

**Decided: after, as a new story.** Neither the SQLAlchemy-leak fix nor the live-eval fix happens
inside this retrospective. Gate B's `evidence/epic-5/release-gate-report.json` and the 50-case
dataset-floor decision (lower it with a recorded rationale, or hold) wait until the live-eval story
lands and the suite passes against the configured provider.
