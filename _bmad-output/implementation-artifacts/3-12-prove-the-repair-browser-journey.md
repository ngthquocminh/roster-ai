# Story 3.12: Prove the Repair Browser Journey

Status: in-progress

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As the product team,
we want the repair journey proven correct end to end in the browser before release,
So that the planner can complete draft, run, and comparison work through a reconnect without losing evidence targeting.

## Acceptance Criteria

1. **Given** the browser repair journey through Chat, Runs, and Results **When** one end-to-end test executes draft, Run optimization, mid-run reconnect, terminal outcome, and comparison **Then** the same run ID and prior content survive the reconnect, each literal state renders its required text, and every evidence link resolves to its exact target **And** a regression in evidence targeting or journey completion blocks release. (NFR29, UX-DR10, UX-DR13) [Source: epics.md:1124-1129]
2. **Given** the same journey **When** the automated accessibility suite established in Epic 1 runs against its surfaces **Then** keyboard operability, focus management, and semantic status text pass without manual assistive-technology verification **And** an accessibility regression blocks release. (NFR18, NFR20, NFR29) [Source: epics.md:1131-1134]

## Facts This Story Depends On

Named explicitly, per this project's "facts this story depends on" pass. Every fact below is written down somewhere citable before any Decision relies on it.

- **`docs/DOMAIN-MODEL.md` does not apply to this story.** This story touches no demand row, metric calculation, or assignment family — it drives an already-built browser journey through Chat/Runs/Results and asserts literal rendered text. Recorded explicitly so nobody re-derives the family/unit rule where it does not belong.
- **The route tree this journey crosses** (`frontend/src/App.tsx:43-73`): `/scenarios/:scenarioId` → `ScenarioChat` (index), `/scenarios/:scenarioId/data` → `ScenarioData`, `/scenarios/:scenarioId/runs` → `ScenarioRuns`, `/scenarios/:scenarioId/runs/:runId` → `ScenarioResults`. No route changes are implied by this story.
- **Chat selects its conversation from a `?conversation=` query param**, not path segment (`ChatView.tsx` reads it via `useSearchParams`; verified by `frontend/e2e/keyboard-journey.spec.ts:104`'s own navigation to `/scenarios/${SCENARIO_ID}?conversation=${CONVERSATION_ID}`). This story's new spec must navigate to Chat the same way — `/scenarios/${SCENARIO_ID}?conversation=${CONVERSATION_ID}` — reusing `apiStubs.ts`'s existing `CONVERSATION_ID` constant, not a bare `/scenarios/${SCENARIO_ID}`.
- **The Chat → draft → run wire, verified live at story creation:**
  - `Composer` (`frontend/src/features/chat/Composer.tsx`) calls `onSend`, which is `useSendMessage` (`frontend/src/hooks/useSendMessage.ts`) → `POST /api/v1/conversations/{conversation_id}/messages`.
  - The persisted turn produces a `draft` activity (`ActivityTimeline.tsx:286-295`) carrying `proposal_id` and `consequence_summary`, rendered by `DraftCard` (`frontend/src/features/chat/DraftCard.tsx`), which reads `GET /api/v1/proposals/{proposal_id}` via `useProposal`.
  - `DraftCard`'s "Run optimization" button calls `useStartScheduleRun` (`frontend/src/hooks/useStartScheduleRun.ts`) → `POST /api/v1/schedule-runs`, body `{ proposal_id, expected_resource_version }`. On success it renders an in-card acknowledgement region (`aria-label="Optimization queued"`) naming the run ID and status, but does **not** navigate to Runs/Results itself.
  - `RunsTable` (`frontend/src/components/runs/RunsTable.tsx:171-186`) renders a `Link` to `/scenarios/{scenarioId}/runs/{run.schedule_run_id}` labelled "View progress" while the run is non-terminal and "View results" once terminal — this is how the journey moves from Runs into Results.
- **The Results rendering contract, verified live at story creation** (`frontend/src/routes/ScenarioResults.tsx`):
  - `useScheduleRunResult(runId)` (`frontend/src/hooks/useScheduleRunResult.ts`) is a plain `useQuery` against `GET /api/v1/schedule-runs/{run_id}/result` with `retry: false` and **no** `refetchInterval` — there is no live push to this page. Re-reading it is either an explicit "Refresh" button click or a fresh mount (navigation or reload).
  - `NON_TERMINAL = {solver_queued, solver_running, cancellation_requested}` renders `ProgressCard` (literal status text + accepted timestamp only — no percentage, spinner, or ETA, by design per Story 3.7 Trap 1).
  - `run.status === "solver_completed"` with both `candidate` and `comparison` present renders `ComparisonSummary` plus a candidate-schedule list and an "Evidence" section.
  - Every other non-`solver_completed` terminal status (`solver_infeasible`, `solver_timed_out`, `solver_cancelled`, `solver_failed`) renders `TerminalOutcomeCard`.
  - The run ID lives in the URL (`:runId` route param), not component state — a reload re-derives it from the URL and re-fetches, which is the mechanism UX-DR10's "recovery must retain the same run ID" already rests on.
- **The Results page's "Evidence" list is plain text, not a link, verified live at story creation** (`ScenarioResults.tsx:38-41`): `comparison.evidence_refs.map(ref => <li>{ref.group}: {ref.record_id}</li>)` — no `EvidenceLink`, no jump-to-target, no `Return to claim`. This is different from Chat's claim segments, which **do** carry a working evidence jump (`EvidenceLink`, Story 2.8, already proven end-to-end by `frontend/e2e/keyboard-journey.spec.ts`'s second test: "jumps to exact evidence and returns to the invoking link with keyboard only"). See Decision 3.
- **No schedule-run SSE stream is wired into the frontend today.** The backend exposes `GET /api/v1/schedule-runs/{run_id}/events` (`backend/api/routers/schedule_runs.py:474-527`, an SSE endpoint reusing `StreamCursorV1`), but no frontend hook consumes it — `ScenarioResults`/`ScenarioRuns` are REST-polled-on-demand only. Only Chat has a live stream (`useConversationStream`, `EventSource` against `.../events`). See Decision 2.
- **`installApiStubs` (`frontend/e2e/support/apiStubs.ts`) is GET-only today** (`request.method() !== "GET"` → 405, line 106-108) and has no route pattern for `.../messages`, `.../proposals/...`, `.../schedule-runs...`, or `.../events`. Every existing browser spec (`accessibility.spec.ts`, `keyboard-journey.spec.ts`, `layout-accessibility.spec.ts`, `reduced-motion.spec.ts`, `responsive.spec.ts`) exercises only Epic 1's read-only Fixture Catalogue and Scenario Data surfaces — **none** visits `/scenarios/:id` (Chat, index route), `/scenarios/:id/runs`, or `/scenarios/:id/runs/:runId`. This is genuinely new Playwright coverage, not an extension of an existing spec's assertions.
- **Component-level accessibility coverage for the repair surfaces is partial.** `DraftCard`, `ComparisonSummary`, and `TerminalOutcomeCard` have jsdom/axe coverage (`frontend/src/test/accessibility-contract.test.tsx`; `ComparisonSummary.test.tsx`; `TerminalOutcomeCard.test.tsx`). `ProgressCard`, `RunsTable`, `ScenarioRuns`, and `ScenarioResults` do not appear in any axe-asserting test file — verified by a repo-wide grep at story creation. No real-browser (Playwright) axe, keyboard, focus-management, zoom, or reduced-motion pass exists for any of these three routes.
- **The Gate A wiring precedent for a proof story's release-blocking artifact** (`backend/scripts/gate_a_checks.py`): each `GateACheck` names one `invariant` (from `ALL_INVARIANTS`); an evidence-bound check (`evidence_path=`) and a test-bound check (`test_files=` + `runner=`) may not be combined on the same entry (`__post_init__`, line 139-148) — they must be split, exactly as Story 1.10 split `accessibility_browser_layer` (playwright test files) from `accessibility_evidence` (the evidence JSON). Story 3.11 added a new `NFR29_GATES` `Invariant` (`recovery_and_idempotency`) rather than overloading an existing one, because its proof was a genuinely new release-blocking concern; its own code-review finding record (`3-11-...md` Review Findings) is the cautionary example of what happens when the artifact is generated but never registered — Gate A reports green regardless.
- **Evidence-generator precedent splits into two shapes already in this repo, not one.** Stories 3.10/3.11 built bespoke `backend/evals/*_report.py` generators because their proof aggregated dozens of independent pytest node results across several failure modes and needed `subprocess.run` orchestration. Stories 2.4 and 3.5 instead used a thin one-off script (`backend/scripts/generate_sse_replay_evidence.py`, `generate_run_event_latency_evidence.py`) that parses one marker out of a captured log and calls `resolve_bindings()` directly — no node aggregation, because the thing being proven is one measurement, not a matrix of failure modes. Story 1.10's `evidence/story-1.10/...json` matches the thin-script shape in its output (a `results` dict of named pass/fail strings) even though its own generator was never captured in `backend/scripts/`. See Decision 5.
- **`NFR27`'s eleven binding keys are non-negotiable and derived, not typed** (`backend/scripts/evidence_binding.py::resolve_bindings`, `DECLARED_BINDING_KEYS`/`DERIVED_BINDING_KEYS`): `dataset`, `scenario`, `code`, and `image` are resolved by the function and may not be supplied by a caller; everything else must be declared with a real reason, never omitted.

## Decisions

**1. This is a proof story: no new capability, route, or contract.** Every command this journey exercises (`POST /api/v1/conversations/{id}/messages`, `POST /api/v1/schedule-runs`, the four read endpoints) already exists and is already an approved Gate A write path (`docs/GATE-A-RUNBOOK.md`'s approved-write-surface table). This story adds test infrastructure (a Playwright stub extension and two new specs) and an evidence/Gate-A registration — it does not add or change an API route, a React component's behavior, or a database column. If implementation surfaces a genuine product defect (not a test-infrastructure gap) while driving the journey, follow Story 3.10/3.11's own precedent: record it as a review finding or an Honest Gap, do not silently patch product behavior to make a test pass without calling it out.

**2. "Mid-run reconnect" proves the REST/URL contract (a full navigation or reload while a run is non-terminal), not the SSE wire protocol.** The Facts above establish that `ScenarioResults` has no live stream — it reads the run by URL param on mount and refetches on request. UX-DR10's exact wording is "recovery must retain the same run ID", which is a statement about what a reload/reconnect must show, not about `Last-Event-ID` replay semantics. The SSE wire-level reconnect/replay contract is **already proven** at two other layers this story does not need to re-prove: `backend/tests/test_schedule_run_stream_api.py` (API-level cursor replay, cited by Story 3.11 Decision 2's table) and `useConversationStream.test.tsx` (frontend hook state machine, unit-level). This story's "reconnect" step is therefore: navigate away and back (or `page.reload()`) to `/scenarios/{id}/runs/{runId}` while the stubbed run is `solver_running`, and assert (a) the URL still names the same run ID, (b) a fresh mount's `GET .../result` renders the identical `ProgressCard` state, (c) no prior-page component state was required for correctness. **Do not** attempt to fixture a live incremental `EventSource` stream through Playwright's `route.fulfill` — its body is a single static response, not an append-only generator, so it cannot simulate a real SSE frame arriving after the page has already connected; a future story that needs to prove that would require a local test server, which is out of scope here (see Honest Gap b).

**3. "Evidence targeting" (AC1) is satisfied by exercising Chat's already-proven evidence jump inside this same journey — not by adding a working evidence link to the Results page.** The Facts above show the Results page's evidence list is plain text with no jump/return affordance; making it interactive would be new product behavior this story's own Decision 1 rules out, and neither AC cites UX-DR8 (the evidence-link decision) or the Story 2.8 ACs — they cite UX-DR10/UX-DR13, which are about run progress and terminal outcomes. Read together with the epics.md heading ("...without losing evidence targeting"), the intended proof is: the claim that grounds the draft (rendered in Chat before/alongside the `DraftCard`) still carries a working `EvidenceLink` → jump to Scenario Data → `Return to claim`, exercised as one step of the same end-to-end run, reusing the exact mechanism `frontend/e2e/keyboard-journey.spec.ts`'s second test already proves in isolation. If this reading is wrong, escalate rather than silently building a new Results-page evidence-link feature — that is a UX-DR8-shaped change the frozen AC text does not name.

**4. Extend `installApiStubs`/`apiStubs.ts` in place; do not fork a second stub module.** Add the four missing route handlers (`POST .../messages`, `GET /api/v1/proposals/{id}`, `POST /api/v1/schedule-runs`, `GET /api/v1/schedule-runs` list, `GET /api/v1/schedule-runs/{id}/result`) to the same `page.route("**/api/v1/**", ...)` handler `apiStubs.ts` already installs, following its existing `json(route, body, status)` helper and `common` envelope fields. Two reasons: (a) every existing spec that visits Scenario Data through this journey (e.g. the evidence-jump step, Decision 3) needs the SAME stub instance active, and a second `page.route` registration on an overlapping glob races with the first; (b) `apiStubs.ts` already owns the fixture-derived `SCENARIO_ID`/`SCENARIO_VERSION_ID`/`CONVERSATION_ID` constants this journey's stubs must reuse, and duplicating them in a second file is exactly the kind of drift Trap 4 below warns about.
   - **4a. Run-status progression is driven by an explicit test-controlled counter, not wall-clock timing.** Close over a mutable `{ resultCallCount: 0 }` (or similar) inside `installApiStubs`'s route handler; the FIRST `GET .../result` call for the scripted run returns `solver_running`, every call after the test's own reconnect step returns `solver_completed` with a full `candidate`/`comparison` payload. This keeps the journey fully deterministic (NFR26) and ties the "mid-run" state to a step the test itself performs (send message → run → first Results view), not to a `setTimeout` race.
   - **4b. The scripted `draft` activity and `proposal` reuse the SAME resolved entity/evidence shape `apiStubs.ts` already ships** (`EVIDENCE_RECORD_ID`, the `demand` group's `outbound:0` record) so the evidence-jump step (Decision 3) targets a record the contract fixture actually has, rather than inventing a second fixture record that could silently stop matching `pageFor`'s filter logic.
   - **4c. The `POST .../messages` stub does not attempt to simulate a real agent turn.** It accepts any well-formed body and returns a fixed acceptance response; the resulting `draft` activity is served by making the SAME conversation's `GET .../timeline` stub return the additional `draft` item once the messages POST has been observed (tracked by the same counter object) — mirroring how the real `finalize_agent_run` path appends to the timeline, without executing any model logic. `models.ALLOW_MODEL_REQUESTS = False` (Story 2.2) does not apply here — this is a pure frontend fixture with zero backend/model surface, like Story 3.11's own worker-entrypoint tests noted for themselves.

**5. Evidence generation follows the Story 2.4/3.5 thin-script precedent, not the Story 3.10/3.11 report-generator precedent.** This proof is one Playwright spec's pass/fail across two browser projects plus a small set of named journey/accessibility assertions — not a matrix of independently-orchestrated pytest nodes across several failure modes. Add `backend/scripts/generate_repair_journey_evidence.py`, mirroring `generate_sse_replay_evidence.py`'s shape exactly: parse a captured Playwright run (JUnit XML via `frontend/e2e/support/streaming-junit-reporter.mjs`, the same reporter Gate A already uses — do not invent a second capture mechanism), assert both `chromium` and `msedge` ran and passed by name, call `resolve_bindings()` for the eleven NFR27 keys, write `evidence/story-3.12/repair-browser-journey.json` with a `results` dict of named pass/fail strings matching Story 1.10's shape (`axe_browser`, `keyboard_operable`, `focus_management`, `journey_completion`, `run_id_survives_reconnect`, `evidence_link_resolves`, etc. — name them to what Decision 2/3 actually assert, not generically). Register the new file in `regenerate_evidence.py`'s `EVIDENCE_FILES` tuple so it is re-bindable like every other evidence file, following that module's own stated convention.

**6. Gate A registration: one new NFR29 invariant for journey completion/evidence-targeting; extend the EXISTING accessibility invariant for AC2.** AC1 and AC2 are different concerns proven by different mechanisms, matching how Story 1.10 itself split `accessibility_browser_layer`/`accessibility_evidence` from the negative-mutation/parity invariants it did NOT touch:
   - **6a.** Add `Invariant("repair_browser_journey", "Repair browser journey (draft, run, reconnect, terminal outcome, comparison, evidence targeting)", "NFR29")` to `NFR29_GATES` in `backend/scripts/gate_a_checks.py`, following `recovery_and_idempotency`'s exact precedent (a genuinely new release-blocking concern, not a re-purposed existing one).
   - **6b.** Add a `GateACheck(check="repair_browser_journey_proof", story="3.12", invariant="repair_browser_journey", runner="playwright", test_files=("frontend/e2e/repair-journey.spec.ts",), required_projects=("chromium", "msedge"))` for AC1.
   - **6c.** Add a `GateACheck(check="repair_browser_journey_evidence", story="3.12", invariant="repair_browser_journey", evidence_path="evidence/story-3.12/repair-browser-journey.json")` — separate entry, per `GateACheck.__post_init__`'s refusal to combine `test_files` and `evidence_path` on one check (Facts above).
   - **6d.** For AC2, do **not** create a third invariant — extend the EXISTING `accessibility_browser_layer` check's `test_files` tuple (invariant `accessibility_and_responsiveness`, already NFR29-gated) with the new accessibility spec (`frontend/e2e/repair-journey-accessibility.spec.ts`), because AC2's own text says "the automated accessibility suite established in Epic 1" — it is explicitly the SAME suite gaining new surface coverage, not a new one.

## Honest Gaps

- **(a) The Chat-side "evidence targeting" reuse (Decision 3) is this story's own interpretation of an ambiguous AC/epics pairing, not a directly cited UX-DR.** If a future reviewer determines AC1 actually intends a working evidence link ON the Results page, that is new frontend work (a UX-DR8-shaped `EvidenceLink` wired to `comparison.evidence_refs`) this story does not build and did not budget for. Flag rather than silently expand scope if this reading is challenged at review.
- **(b) True SSE mid-stream reconnect (a frame arriving on `.../schedule-runs/{id}/events` while the browser is genuinely connected) is not fixtured by this story (Decision 2).** Playwright's `route.fulfill` cannot simulate an append-only stream; proving that would need a local test HTTP server serving real incremental SSE frames, which is a materially larger testing-infrastructure investment than this story's budget. The wire-level replay contract stays proven at the two layers named in Decision 2 (backend Postgres test, frontend hook unit test) and is not re-proven here.
- **(c) Cancel is not part of this journey.** The AC's Given clause names "draft, Run optimization, mid-run reconnect, terminal outcome, and comparison" — no cancellation step. `useCancelScheduleRun`/`CancelButton` already have their own coverage from Story 3.7; this story does not touch them.
- **(d) The repair surfaces carry three of the five Epic 1 browser-accessibility dimensions, not five.** `repair-journey-accessibility.spec.ts` runs axe, keyboard/focus, and literal semantic status text against Chat, Runs, and Results. It performs **no** 200%-zoom/reflow pass, no text-spacing pass, and no `prefers-reduced-motion` pass — those stay proven only on Epic 1's Scenario Data surfaces (`layout-accessibility.spec.ts:85,105`, `reduced-motion.spec.ts`, `responsive.spec.ts`, all of which target `demandUrl` and `/` only). AC2's *Then* clause names only keyboard operability, focus management, and semantic status text, so no AC is unmet; but Trap 1 defines the browser layer as including zoom/reflow and reduced motion, so the new spec is a partial member of the suite it joined via Decision 6d. `NFR20` was therefore **removed** from the evidence artifact's `requirements` and `policy` bindings at review rather than claimed on coverage that does not exist. **Owner/revisit trigger:** the first story that extends browser-layer accessibility onto the repair surfaces.
- **(e) Two product-code changes were made under a story whose Decision 1 scopes product behavior out.** `frontend/src/components/ui/button.tsx` (shared `destructive` variant: tinted → solid, after a real-browser axe reading of 3.82:1 on `Reject proposal`) and `frontend/src/routes/ScenarioResults.tsx` (focus the results heading on route entry, after keyboard navigation left focus on `<body>`). Both are genuine defects surfaced by Task 3/4 and are permitted by Decision 1's own escape clause — but that clause requires them to be "recorded as a review finding or an Honest Gap", and at hand-off they appeared only as Debug Log, Completion Notes, sprint-status, and Change Log prose. Recorded here at review. Note the `button.tsx` change is a **shared primitive** with 14+ call sites across Chat, Runs, Evidence, and the Fixture Catalogue, not a single-button fix; its light-mode treatment is axe-verified on those surfaces, and its `dark:` arm is not, because nothing in `src/` applies the `.dark` class. See Review Findings.

## Traps

The quietest first:

1. **Treating a component passing jsdom/axe (`DraftCard`, `ComparisonSummary`, `TerminalOutcomeCard`) as proof AC2 is already satisfied.** It is not — AC2 explicitly names "the automated accessibility suite established in Epic 1", which for every prior Gate A surface has meant BOTH `accessibility_component_layer` (jsdom/axe) AND `accessibility_browser_layer` (real Chromium+Edge: axe, keyboard, focus, zoom/reflow, reduced motion). `ProgressCard`/`RunsTable`/`ScenarioRuns`/`ScenarioResults` have neither layer today (Facts above); a partial pass on the three components that DO have jsdom coverage is not the same claim.
2. **Building a second stub module or a second `page.route("**/api/v1/**", ...)` registration instead of extending `apiStubs.ts` in place** (Decision 4) — two overlapping Playwright route handlers on the same glob race unpredictably rather than composing.
3. **Simulating "mid-run reconnect" with a `setTimeout`/`waitForTimeout` race instead of a test-controlled counter** (Decision 4a) — a wall-clock race is exactly the non-determinism NFR26 forbids for CI evidence, and would make the "mid-run" state flaky rather than a reliable, always-reproducible gate.
4. **Wiring a real `EvidenceLink` onto the Results page to make Decision 3's reading trivially true** — that is new product scope Decision 1 explicitly rules out; if AC1's evidence-targeting clause cannot be satisfied by the existing Chat-side jump, escalate (Honest Gap a), do not quietly ship the feature to close the gap yourself.
5. **Reading `ScenarioResults`'s "no invented percentage/ETA" contract (Story 3.7 Trap 1) as license to skip asserting the run's literal, exact status text** — the AC requires "each literal state renders its required text"; assert the exact rendered strings (`ProgressCard`'s status badge text, `TerminalOutcomeCard`'s reason text, `ComparisonSummary`'s heading) rather than only asserting the page didn't crash.
6. **Padding the golden dataset or adding `backend/evals/golden/**` cases toward `evals/README.md`'s "Stories 2.9, 3.10–3.12, and 4.5–4.6 contribute" line.** This story has no LLM-scriptable turn (`POST .../messages` is fully stubbed, not routed through a real `AgentRuntime`/model double) — `evals/README.md`'s line stays unmet by this story for the same structural reason Stories 3.10/3.11 already recorded against themselves. Re-derive the current dataset floor at Task 1; do not cite Story 3.11's cited figure as current.
