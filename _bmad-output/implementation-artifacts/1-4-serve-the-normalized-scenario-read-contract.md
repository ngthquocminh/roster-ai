# Story 1.4: Serve the Normalized Scenario Read Contract

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As the scenario platform,
we want one versioned normalized scenario read contract,
so that direct inspection and assisted investigation cannot disagree about source facts.

**[Technical Enabler] — no planner-visible outcome.** The Scenario Data workspace that renders this contract is Story 1.7's acceptance boundary. This story is accepted entirely through versioned API contract, cursor/window, and count tests. **There is no frontend UI work in this story** beyond regenerating the generated OpenAPI client types (Task 3) — no route, no hook, no component.

**Depends on:** Story 1.1 (done) — `scenario_version.payload` JSONB (the raw fixture), forced RLS, `shiftmind_runtime` SELECT grant. Story 1.3 (done) — `get_site_context`, the `scenario`⋈`scenario_version` join and its multi-version "latest" resolution convention, the `Depends(get_catalogue_reader)`-style port seam, and the RFC 7807 problem-details middleware.
**Unblocks:** Story 1.5 (evidence-target resolution reuses this same read path and `record_id` scheme), Story 1.7 (Scenario Data workspace consumes these endpoints), Story 1.8 (sorting/filtering layers on top of this cursor contract), Story 1.9 (viewer/agent parity and mutation-denial audits target these endpoints), and Epic 2 Story 2.5 (the agent inspect capability calls the same scenario-read use case, not a second interpretation of `payload`).

## Acceptance Criteria

1. **Given** an authorized fixture version, **when** `ScenarioProjectionV1` is requested, **then** it returns version/checksum metadata, horizon and IANA timezone, work areas/tasks, workers/qualifications/availability, demand intervals, baseline assignments, locks, constraints/objectives, and version-bound evidence references, **and** all schedule intervals use integer-minute half-open offsets from a UTC horizon. *(FR24, AD-4, AD-20)*

2. **Given** a projection group larger than one response window, **when** it is read, sorted, filtered, or deep-linked, **then** bounded cursors expose total/matching counts and deterministic stable-ID tie-break ordering. *(UX-DR14, UX-DR15, UX-DR24)*

3. **Given** the normalized scenario query and its errors, **when** frontend and backend contracts are generated and consumed, **then** FastAPI publishes versioned OpenAPI, the SPA uses generated endpoint types through one `openapi-fetch` client, and failures render stable RFC 7807 problem details with safe correlation/resource/version fields, **and** transport DTOs do not become domain authority. *(AR13)*

4. **Given** the NFR35 measurement fixture (the largest Gate A fixture, warm process and warm database, local or CI reference environment, three consecutive deterministic runs), **when** the initial window of each Scenario Data group is requested, **then** every run completes server-side request handling within 2 seconds, measured from request receipt to response completion, **and** the measured values are recorded as release evidence and a miss blocks implementation acceptance of this story. *(NFR35)*

## Dev Notes

- **No baseline assignments or locks yet — and this story must not fabricate them.** Same shape of decision Story 1.3 made for `baseline_schedule_version`: the operational baseline is owned by the scheduling aggregate (AD-22) and doesn't exist until Epic 3 (`ScheduleVersionV1`, produced by a completed `ScheduleRun`) and Epic 4 (atomic promotion). Nothing in the current raw fixture represents a committed assignment or a planner lock — `Roster Profile` is a worker's *committed availability window*, not a task assignment, and there is no lock concept anywhere in `payload`. `AssignmentV1`/`LockV1` are defined now (contract stability) but always return empty pages. When Epic 3/4 land, only the adapter query changes — the contract and the empty-page test both already exist as the documented starting state.
- **Time and timezone.** The raw fixture's datetimes (`Scenario Range.PeriodStartDate`, `Roster Profile.StartDateTime`, `Outbound Workload.StartDateTime`, etc.) are naive local wall-clock strings with no embedded offset or zone — `ingest/scenario_time.py`'s existing `parse_dt` only ever produces naive `datetime`s for exactly this reason. AD-20 requires `horizon_start` as a UTC instant plus an IANA `site_timezone` and integer-minute half-open offsets. **[ASSUMPTION]** No IANA zone is recorded anywhere in the product yet (PRD/UX/architecture are silent on it beyond "DC" terminology; `EBA` — Enterprise Bargaining Agreement — and the grade/casual/full-time vocabulary are distinctly Australian workplace-relations terms). Use `zoneinfo.ZoneInfo("Australia/Sydney")` (stdlib since 3.9, no new dependency — AR27) as the fixed `site_timezone` for every scenario in this MVP: localize each parsed naive datetime in that zone, then convert to UTC before differencing against `horizon_start` to get `start_minute`/`end_minute`. Computing every offset as an independent UTC-instant difference (never as wall-clock arithmetic) means DST folds self-correct without special-casing; current fixture date ranges (early June, Southern Hemisphere winter) don't cross a transition regardless. Record this as a flagged assumption in your completion notes — it's a product decision precedent, not a fact this story can verify.
- **Reuse `ingest/input_adapter.py`'s field selection, not its skip rules.** It's the proven mapping from raw table names to normalized concepts (which field is the rate override, which loop expands `Inbound Workload.Tasks[]`, etc.) and reusing it is exactly what AD-4 asks for — the viewer and the solver must read facts the same way. But its *skip* rules (drop members with no window/qualification, clip demand to horizon, skip non-positive volume) exist to keep `SchedulingProblem` solver-sized; they are not "the facts." A planner inspecting Scenario Data must see the unfiltered fixture, so re-derive without those skips. `ingest/input_adapter.py` is not frozen legacy (unlike `store/`, `services/`, `llm/`) — it's fine to read for pattern, but this story's own normalization is new code in `adapters/postgres/scenario_projection.py`, not a shared call into it (its output type, `SchedulingProblem`, is the wrong shape and its skip rules are wrong for this use).
- **Reuse Story 1.3's "latest version" resolution verbatim.** `PostgresScenarioCatalogueReader`'s `_VERSION_ORDINAL` expression is the one and only definition of "the governed version of a fixture" in this codebase (numeric-digit ordinal, text/id tie-break — chosen specifically to survive `v10` sorting after `v2`). If this story's adapter picked a different resolution, the catalogue and the projection could disagree about which version is current for the same `scenario_id`, which is precisely the "viewer/agent fact drift" AD-4 exists to prevent. Duplicate the expression with a comment pointing at its sibling (extracting a shared helper is fine too, but not required).
- **Split HTTP contract, one logical contract.** The Structural Seed's `ScenarioProjectionV1` table (`ARCHITECTURE-SPINE.md`) describes the conceptual full record — scenario/version IDs, checksum, horizon, timezone, all seven groups, evidence refs. AC #2 requires groups larger than one window to be cursor-bounded, so the wire-level HTTP contract is deliberately split into the overview endpoint plus six per-group windowed endpoints rather than one unbounded JSON blob. This is a documented HTTP-shaping decision under AD-20, not a deviation from it.
- **Evidence references, minimally.** AC #1 asks for "version-bound evidence references." This story provides exactly what it can honestly populate: every group response carries `scenario_id` + `scenario_version_id` at the page level, and every item carries a stable `record_id`. That triple (`scenario_version_id`, `group`, `record_id`) is sufficient to cite a fact. **Do not build a full `EvidenceRefV1` locator type or exact-target-outside-window resolution here** — those are Story 1.5's entire acceptance boundary (out-of-window lookup, missing/unauthorized/version-mismatch distinct failures). Building any of that now duplicates work Story 1.5 is explicitly scoped to do next.
- **No migration.** Every field this story needs already exists in `scenario_version.payload` (JSONB, Story 1.1) or is computed in Python. No new table, column, or Alembic revision. `alembic check` must report zero drift, same as Story 1.3.
- **Domain purity (AD-1).** `backend/application/contracts/` and `backend/application/ports/` must not import SQLAlchemy, FastAPI, or Pydantic. All normalization/SQL code lives in `backend/adapters/postgres/scenario_projection.py`; all Pydantic response models live in `backend/api/schemas.py`.
- **No new dependency at this gate (AR27).** `zoneinfo` is Python stdlib (3.9+); everything else needed is an existing repository lock. Do not add `pytz` or any date library. Do not touch `uv.lock`/`package-lock.json`.
- **Test conventions:** same as Story 1.3 — `backend/tests/test_*.py`, `uv run --frozen pytest`; PostgreSQL-backed tests use `@pytest.mark.postgres` and the `governed_postgres_engine`/`fresh_postgres_database_url` fixtures in `backend/conftest.py`, which skip cleanly with no local PostgreSQL service.
