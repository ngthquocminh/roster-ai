Turn Routing Switchyard

In conversation f0cdeca6, the scheduling assistant sang a song and wrote quadratic-equation Python instead of staying on scheduling. This session designed the switch that runs before every turn: a fast decision model, TypeSafe Jev, reads the planner’s message and sets one route, and each route gets a smaller prompt built from sections of the master prompt.

Box 1 · 20 ideas

Morphological Analysis

The session split the router into nine parameters and generated options for each. Every idea sits in the row of the parameter it answers.

Placement 1 option

Decide the route in the API route, before runtime_factory, so one decision picks instructions, granted capabilities and output types together.

Router input 3 options

Router state = latest message + previous planner message + the first ~300 chars of the previous agent reply: enough to resolve “yes, do it”.

Include the previous turn’s route in router state, so short follow-ups stay on the path they came from.

Add snapshot flags (has_draft, run_in_progress, completed_candidate, pending_approval) to detect planner_control asks like “approve it”.

Label set 3 options

A closed route vocabulary, TurnRouteV1 = Literal[scheduling, direct, out_of_scope, …], in the same style as RefusalReasonV1.

A two-level decision asked in ONE Jev request: in_domain yes/no, then direct-vs-tools, answered in parallel.

Replace one opaque 5-way choice with orthogonal noul probes (needs_schedule_data, is_injection, is_followup, is_off_topic) combined by an application decision table.

Decision rule 3 options

Asymmetric per-label thresholds: out_of_scope 0.9, direct 0.8, planner_control 0.85. Scheduling needs none because it is the default.

Leave the full path only when both the chosen option’s probability and Jev’s confidence clear the threshold.

Margin rule: take a special path only if p(label) − p(scheduling) is at least 0.6, comparing explicitly against the safe default.

Fallback 1 option

A TurnRouter application port: a Protocol that never raises and returns closed error codes, with a Jev adapter in adapters/routing, mirroring ClaimSupportChecker.

Generator 2 options

The out-of-scope reply can be an application template with no LLM call: zero tokens and impossible to jailbreak.

Direct path = a small LLM prompt with prose output plus an escalate output tool.

Composition 2 options

Represent each path as a frozen TurnPathV1 manifest: name, instruction sections, granted capability names, output types, history bound, include_workflow_context flag.

Special paths skip the workflow snapshot and use a ~6-message history bound. This is the main token saving.

Tool grant 1 option

Validate path manifests at startup like capability manifests (the IncompleteManifestError pattern): every referenced section and capability must exist.

Rollout 4 options

Settings: agent_router_mode off/shadow/on, per-label thresholds, router timeout. Reuse the grounding provider/key resolution.

Extract a shared JevClient (post, batching, closed error codes) used by both the claim checker and the router.

Route telemetry on the span: label, probability, confidence, latency_ms, closed error code, acted flag.

Optionally carry the route in the agent_response activity payload for analytics, avoiding a DB migration.

Chaos Engineering

Break the router every way you can, and keep what survives. Each tile pairs a break with the design move that survives it.

19 breaks19 survive
Break

Jev returns a 5xx or a transport error.

Survives

The turn takes the full path (fail-open) and telemetry counts it. The turn never fails because of the router.

Break

The router is slow.

Survives

It gets its own tight timeout (~1s), separate from the grounding checker’s 5s. Timeout → full path.

Break

A direct answer contains digits or scenario entity names.

Survives

The escalate validator on the direct path reruns it on the full path automatically.

Break

A scheduling question is wrongly refused.

Survives

The refusal’s next_step tells the planner how to rephrase it as a schedule question.

Break

Greeting + request: “hi, how many pickers Wed?”

Survives

Direct’s criteria say ONLY greeting or small talk. Any schedule request means scheduling.

Break

Off-topic + scheduling: “write python to count my workers”.

Survives

It routes to scheduling, where the scope rule answers only the in-scope part.

Break

An injection hides inside a real request.

Survives

It reaches the full path. The router is not the security boundary; tool grants and validators are.

Break

Any misroute at all.

Survives

Invariant: every special path is strictly less capable than the full path, so a misroute can only lose capability, never gain it.

Break

Vietnamese greetings and questions.

Survives

Multilingual messages must route correctly: add them to the routing eval set.

Break

A very long message, like a pasted CSV.

Survives

The router state is truncated. Over Jev’s 32k limit → full path.

Break

An empty, whitespace-only or emoji-only message.

Survives

It routes to direct.

Break

An approval resume arrives.

Survives

It bypasses the router: it continues a turn already on the full path.

Break

A reply to a clarification: “the second one”, “Ana B.”

Survives

A deterministic pre-rule forces it to scheduling.

Break

A follow-up to a clarification, draft or approval request.

Survives

Deterministic pre-rules run before Jev: if the previous agent activity was one of those, go straight to scheduling.

Break

“what did we discuss?” on a path with short history.

Survives

Direct cannot recall earlier facts, so this routes to scheduling, where summaries recompute numbers.

Break

Escalations climb, and each one doubles LLM calls.

Survives

Track the escalation rate; if it climbs, raise the direct threshold.

Break

Routing-eval results go stale.

Survives

Pin the Jev model version for routing (e.g. jev-1.13, not jev-latest).

Break

A live-eval regression with no obvious culprit.

Survives

Put the route label into eval reports, so it can be attributed to routing or to answering.

Break

The router lands in CI.

Survives

A CI stub router always returns scheduling, so every existing test is unchanged. Router tests use a scripted stub.

Box 3 · 10 ideas

Nature’s Solutions

Biomimetic borrowing: reflexes, the immune system, triage, membranes. Each card takes a mechanism from nature and turns it into a router rule.

Spinal reflex

An exact-match set of trivial greetings goes to direct with no Jev call: zero latency, zero cost.

Immune self / non-self

Define the scheduling domain positively and broadly. The out_of_scope criteria = “clearly unrelated to workforce scheduling or this app”.

ER triage

Under uncertainty, escalate to the highest-care path. The router is triage; the full path is the senior doctor.

Bee waggle dance

Log routing decisions and outcomes in shadow mode, and fit per-label thresholds from the calibration curve.

Octopus arms

Each path is a semi-autonomous arm with its own small prompt, owned by its manifest.

Cell membrane

The path manifest filters which capabilities pass into the runtime: a structural guarantee.

Pheromone cache

Cache route decisions for identical, normalized, context-free messages like “hi”.

Chameleon

The direct path answers in the planner’s language.

Vaccination

Seed the routing eval set with attack prompts and off-topic families: code, songs, math, trivia, weather, personal advice, payroll/HR policy.

Homeostasis circuit breaker

When the router error rate is high, bypass it for N minutes and warn once, like the tier-1 checker.

Box 4 · 5 ideas

Kill the Crown Jewel

Pull one lever at a time and remove a part the design leans on (Jev, the prompt split, the LLM, the escalate valve), then see what still runs.

  • PulledJev

    A cheap LLM (Haiku/Flash) becomes an alternative router adapter behind the same TurnRouter port. Jev is one implementation.

  • PulledAny router

    The FR-6 scope rule in the full prompt is the baseline to compare against, and it ships anyway as defence in depth.

  • PulledThe prompt split

    Special paths reuse the full prompt but restrict tools and outputs. Safety kept, token savings lost, so the split and the router are separable phases.

  • PulledThe LLM on special paths

    planner_control becomes a Jev choice over controls (run/approve/reject/cancel) plus a template reply naming the exact button.

  • PulledThe escalate valve

    The direct threshold must go ultra-conservative (~0.95). The valve is what lets direct be useful.

Box 5 · 9 ideas

SCAMPER

Seven verbs applied to one object: the master prompt, and how to decompose it into sections that each path can compose from.

  1. SSubstitute

    Sections become named constants in an agent/instructions package.

  2. CCombine

    compose_instructions(path) joins sections in canonical order. The full path is byte-identical to today, pinned by a test.

  3. AAdapt

    Each section declares the tools that require it, so granting scheduling_compute automatically pulls in the “Calculated values” section.

  4. MModify

    A test reports estimated tokens per composed path and guards that the direct prompt stays under a budget.

  5. PPut to other use

    The live-eval judge could receive only the sections relevant to the route.

  6. EEliminate

    The “Greetings and capability questions” section leaves the full path only after the router is on and evals pass.

  7. RReverse

    Build paths up from a minimal core (identity + scope rule) shared by every path, instead of subtracting from the master.

  8. +Two more from this box
    • The shared core carries the FR-6 scope rule, so even the full path refuses the off-topic part of a mixed request.
    • Emit a hash of each composed prompt as a span attribute, so eval results can be attributed to a prompt version.

Box 6 · 16 ideas

Starbursting

Who, what, when and how questions about evaluation and rollout, each turned into ideas. The ideas are grouped here under the question they answer.

Evaluation & rollout

What do we test against?

  • A routing eval dataset: JSONL of (history, message, expected_route, must_not_route) across families, ~150 cases.
  • Every existing golden and live-suite prompt is a free “must stay on the full path” negative case.
  • Live suite: add the f0cdeca6 transcript as an off-topic conversation and a mixed one; assert a refusal with reason out_of_scope.

How do we know it’s right?

  • Primary metric: false-exit rate (scheduling messages sent to a special path) ~0. Secondary: special-path recall.
  • Calibrate thresholds from shadow data: highest recall at zero false-exits on the labelled set.
  • A shadow-mode Logfire dashboard panel: route mix and probability histogram per label.

What proves it in CI?

  • Deterministic golden cases inject the route via the stub and assert the path composition: no tools granted on direct, restricted output types.
  • Architecture test: each special path’s capability grant is a subset of the full path’s.
  • Test that compose_instructions('scheduling') equals today’s SCHEDULING_ASSISTANT_INSTRUCTIONS snapshot.
  • Red-then-green: a scripted model writing code on the out_of_scope path must fail once the output restriction exists, and pass without it.

When does the turn wait?

  • Run the Jev call in parallel with the workflow-context DB read (they are independent) to hide router latency on the full path.
  • Speculatively build the full runtime while the router runs; build the small runtime only when a special path wins.

Where does the route show?

  • Carry the route on the activity, so the timeline can show it in a dev/debug view.
  • A planner override, “Ask anyway”, re-sends with force_route=scheduling. Frontend work, parked for the portfolio MVP.

What does it save?

  • Cost/latency evidence per path, before and after (p50/p95, tokens), as a portfolio metric: e.g. how much cheaper greeting turns become.
  • Repeated off-topic attempts never consume main-model budget: cost protection against abuse.

Candidate paths & edge messages

New sidings

7 insights along the way

Signals cleared

What the session concluded between techniques, before it pulled everything together.

  • Special paths are strictly less capable than the full path, so a misroute can only lose capability. The router is not a security boundary and can safely be probabilistic.

  • Orthogonal noul probes combined by an application decision table are more debuggable and tunable than one opaque multi-way choice.

  • Deterministic pre-rules (clarification/draft/approval follow-ups, reflex greetings) remove the riskiest misroutes and many Jev calls.

  • Running Jev in parallel with the workflow-context load hides the router’s latency on the full path.

  • The FR-6 scope rule belongs in the shared core section: defence in depth even when the router misses.

  • Linking prompt sections to the tools that require them makes the later tool-scoped paths almost free.

  • Prompt split, router shadow and acting on routes are separable phases; the split alone is a zero-behaviour change.
