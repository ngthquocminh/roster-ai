# Adversarial Independent-Epic Compatibility Review

**Target:** `ARCHITECTURE-SPINE.md`  
**Review posture:** Assume each epic team reads the spine, implements only its assigned boundary, and obeys every AD literally. If two such implementations can still be mutually incompatible, the spine has not done its job as an independent-epic contract.

**Verdict:** **FAIL — the principles are strong, but the integration contract is not closed.** The spine constrains authority, persistence, and deployment direction while leaving too many shared schemas, ownership rules, transition edges, transaction protocols, cursors, hashes, and rollout semantics open. The following are concrete implementation pairs that can each claim literal AD compliance and still fail when merged.

## Findings

- **The accepted schedule and comparison shapes have no canonical owner or schema.** A scheduling epic can persist an immutable solver result as rows shaped like the current `ScheduleRow` (`contact_id`, `task_id`, `shift_id`, `start_h`, `end_h`) plus floating-point metrics, while a comparison epic can define its equally application-owned immutable contract around `worker_id`, role/work-area IDs, RFC 3339 intervals, money in minor units, and decimal objective components. Both keep framework types out, use CP-SAT results, preserve versions, and provide typed application DTOs under AD-1, AD-2, AD-9, AD-11, and AD-13. They cannot compute a diff, generate evidence, or render a result without an undocumented translation that decides identity aliases, interval rounding, money precision, missing-role behavior, and aggregation semantics. The spine fixes a normalized scenario projection but never fixes the canonical proposal, solver input, schedule version, metrics, schedule diff, or comparison DTOs that at least four epics share.

- **Time normalization is impossible to implement consistently from the existing fixtures.** The brownfield domain uses floating hours from a scenario start, and the fixture timestamps are naive strings such as `2026-06-01T00:00:00`; the spine only says PostgreSQL stores UTC and APIs emit RFC 3339 UTC. An ingestion epic can interpret fixture values as a site's local civil time and convert them to UTC, while an engine/migration epic can treat the same values as already UTC and preserve the current hour offsets. Both expose UTC externally and obey the unit/time convention. Their immutable scenario hashes, evidence record ranges, schedule rows, Wednesday labels, and approval consequence hashes differ by the site offset. No AD chooses a fixture timezone, DST policy, local-day boundary, precision/rounding rule, or canonical conversion between domain offsets and stored instants.

- **“Site baseline” admits two incompatible ownership models.** A governance epic can implement one versioned pointer on `site` (`current_baseline_schedule_version_id`, `baseline_version`), exactly matching the singular site-baseline language. A fixture/scheduling epic can implement a site-owned `site_baseline(site_id, scenario_id, schedule_version_id, version)` so each catalogue scenario has its own current baseline, also reasonably satisfying a versioned site pointer and the selected-scenario journey. Both reject stale inputs and preserve immutable schedules. They disagree about whether selecting another fixture changes the site's operational baseline, whether two scenarios may be compared, which version an approval binds, and what resource owns the optimistic version. The ER diagram does not contain a baseline-pointer entity or cardinality, so promotion and comparison epics cannot independently choose compatible keys or invariants.

- **The manual fallback cannot fit the declared aggregate hierarchy without an unstated ownership decision.** The ER diagram places `JOB`, `PERSISTED_EVENT`, `TOOL_CALL`, and `APPROVAL_REQUEST` beneath `AGENT_RUN`, while AD-15 requires a manual deterministic solver path that remains available when `AgentRuntime` is down and uses the same version, idempotency, site, and audit controls. One epic can create a synthetic “manual” agent run to own every manual job and event. Another can make job/event ownership polymorphic or nullable and attach manual work directly to `SCHEDULE_RUN`. Both preserve durability and never give the model authority. Their foreign keys, provenance traversal, correlation envelope, SSE stream identity, and recovery queries are incompatible. The spine must define whether agent run is mandatory workflow ownership, whether a higher-level workflow/command aggregate owns both paths, or whether manual and agent initiators are distinct explicit variants.

- **Conversation-to-scenario binding is not defined.** A chat epic can bind a conversation permanently to one `scenario_version_id`, making every later message and run inherit that immutable context. A fixture/navigation epic can treat scenario selection as current server/session or route state and permit the same durable conversation to contain agent runs against different explicitly versioned scenarios. Both re-resolve authorization, bind every proposal/run to a scenario version, and preserve exact evidence links. On revisit, one implementation expects a single conversation scenario; the other needs per-message or per-agent-run scenario context. The activity stream, deep links, authorization loaders, and provenance reconstruction cannot agree because neither the ER diagram nor AD-14 states the ownership or change semantics of selected scenario context.

- **The closed run vocabulary is not a closed run state machine.** A worker epic can allow `cancellation_requested -> completed` when the solver crossed its final effect fence before observing cancellation, while a UI/cancellation epic can define `cancellation_requested -> cancelled` as the only legal successor and treat any completed payload as invalid. Each implementation uses compare-and-set commands, keeps terminal states immutable, persists cancellation cooperatively, and emits a terminal result once. Similar ambiguity exists for `queued -> cancellation_requested` versus direct `cancelled`, `running -> timed_out` versus `failed/budget_exhausted`, and whether a recovered expired lease returns to `queued` or remains `running`. AD-7 supplies names but no transition table, command preconditions, race winner, terminal payload invariants, or mapping from solver outcome to run outcome, so independent state-machine and UI epics can both be “closed” and incompatible.

- **`approval_required` has no unambiguous aggregate meaning.** A run epic can keep a feasible schedule run `completed` and put the agent run/approval request into `approval_required`, consistent with the PRD separation between optimization and baseline approval. A workflow epic can move the schedule run itself to `approval_required` until the candidate is accepted or rejected, taking AD-7's inclusion of the status in the shared run vocabulary literally. Both show the required state and avoid implicit promotion. They disagree about whether `completed` is terminal before approval, whether rejection mutates a schedule run, whether a candidate is available from an approval-required run, and which stream emits the terminal outcome. The spine needs distinct state machines for schedule run, agent run, job, approval, and conversation activity, plus an explicit projection into the UI vocabulary.

- **Approval resumption can preserve or replace an agent run with equal AD compliance.** An orchestration epic can persist a paused agent run and resume the same run after an approval decision. An approval epic can close the proposing run, then create a new continuation run correlated to the approved request so no old model checkpoint is re-entered. Both persist all records, bind exact approval, use current authorization, and produce a complete correlation envelope. They cannot share uniqueness rules for tool-call IDs, budgets, event sequences, provenance parentage, or the “same run” UI identity. AD-6 promises durable recovery but does not define cross-state-machine choreography or whether budgets and idempotency span a pause/continuation boundary.

- **Schedule-version creation is ambiguous at the atomic-promotion boundary.** A solver epic can create the immutable candidate `schedule_version` when a run completes, then an approval epic atomically update only the baseline pointer, approval decision, and audit reference to that existing candidate. Another approval epic can read AD-10's “commits the new baseline pointer, schedule version, approval decision, and successful audit in one database transaction” as requiring creation of a promoted schedule version, cloning the immutable candidate into a new baseline version during promotion. Both preserve prior versions, keep candidates isolated, and perform atomic audited promotion. They disagree about the ID bound into the approval, whether the promoted version is byte-identical or derived, which version owns evidence, and what a replay returns. AD-9 and AD-10 need one lifecycle: when candidate and baseline schedule-version rows are created, whether promotion changes classification or creates a derivative, and which IDs/hashes remain invariant.

- **Application-owned transaction boundaries are underspecified for nested use cases.** A capability epic can treat each tool handler as an application command handler with its own unit of work, commit its durable effect and audit, and return to the agent orchestrator. An agent epic can treat the entire accepted tool step as the command and open an outer unit of work that includes the tool-call transition, effect, emitted event, and audit, expecting invoked use cases to join rather than commit. Both follow “application command handlers own unit-of-work boundaries; repositories never commit; tools call use cases.” Merged together, the inner commit can expose an effect while the outer tool-call state rolls back, or the outer transaction can remain open across a model/solver call and hold locks indefinitely. The spine needs an explicit transaction-propagation rule, command/effect granularity, prohibition on remote work inside transactions, and atomicity matrix for each shared workflow step.

- **Reliable audit of rejected attempts can duplicate or disappear.** A policy/approval epic can record a denied or stale consequential attempt in a fresh transaction immediately before returning its application error. An orchestration epic can roll back the failed business transaction and, as AD-12 requires, enqueue/record the same denial in its own separate reliable transaction. Both ensure failures do not disappear when the main transaction rolls back. Without a canonical attempt ID, audit idempotency key, uniqueness rule, or ownership of the failure-recording transaction, one request produces two authoritative events; if each assumes the other owns it, it produces none. AD-8 protects mutating commands/effects but never states whether audit writes themselves use the command idempotency key or how repeated denied attempts are represented.

- **RLS and global worker lease discovery are mutually underdesigned.** An identity/persistence epic can require every repository and database role, including worker access, to set a trusted site context before any query and enforce site RLS on `job`. A worker epic must discover a leaseable job before it knows the job's site, so it can use a cross-site lease query under a narrowly privileged worker role and set site context only after leasing. Both can claim server-derived job scope, current membership/policy checks, least privilege, and RLS defense in depth. Their security models cannot coexist: the first cannot discover work; the second violates the first repository contract and may bypass RLS for more than lease selection. The one-site MVP hides this until scaling. AD-3/AD-17 must choose a queue-discovery security boundary—site-sharded leasing, a security-definer lease function, a dedicated bypass-RLS broker role with constrained SQL, or another exact mechanism—and specify when worker site authority is established.

- **Direct and derived site ownership produce incompatible schemas and RLS policies.** A tenancy epic can copy `site_id` onto every user-owned row so scoped repositories and RLS use simple predicates. A data-model epic can store site only at aggregate roots and derive it through joins (`message -> conversation -> site`, `tool_call -> agent_run -> conversation -> site`), which AD-3 explicitly permits by saying rows may carry or derive site boundaries. Both use trusted context and return indistinguishable not-found responses. Their repository signatures, indexes, foreign keys, partitioning assumptions, audit envelope population, and RLS implementation are incompatible; join-derived RLS also has different deletion and performance behavior. The ER diagram is not enough to tell each epic which tables carry `site_id`, which derive it, or how denormalized site columns are constrained against their parents.

- **Capability registration and discovery have no shared descriptor contract.** One capability epic can use statically imported Python modules whose decorators contribute Pydantic schemas and policy metadata to an in-memory application registry. Another can use a database-backed catalogue of statically bundled module descriptors enabled by deployment feature flags, resolving handlers from stable names. Neither installs capabilities at runtime; both compose grants from trusted context, reject incomplete modules, keep read/write separate, and declare every AD-5 field. They still disagree about the source of truth, startup validation, duplicate-name resolution, feature-flag timing, removal semantics, evaluation-fixture discovery, and what “registered” means to tests. A demonstration module built for one registry will not load in the other. AD-5 needs a versioned application-owned descriptor schema and one registration/discovery lifecycle, even if the concrete adapter remains swappable.

- **Capability versioning does not guarantee queued-work or checkpoint compatibility.** A module team can version a capability as `scheduling.compare.v2` and persist that exact dispatch key on each tool call/job. A runtime team can expose stable `scheduling.compare`, persist a separate schema/tool version, and always dispatch to the currently installed handler with an input upgrader. Both “declare version semantics” and record tool/application versions. During a rolling deployment, an old worker cannot resolve the new key in the first design, while a new worker may reinterpret an old queued payload in the second. Removal of a module can strand persisted runs even though loading/removal itself was governed. No AD defines the persisted capability identity, supported-version window, checkpoint codec, upcaster location, unavailable-version terminal behavior, or rule that deployed workers must retain handlers for all leaseable jobs.

- **The “current explicit run request” is not a transferable authorization artifact.** A conversation epic can mark a planner message or activity item as an explicit run intent and let the compute capability inspect that current state. A manual-run/API epic can create a one-time persisted `run_authorization` record bound to actor, site, scenario/proposal versions, expiry, and idempotency key. Both ensure the model cannot invent compute authority and satisfy AD-5/AD-12. The registry/policy layer cannot be independently implemented because it does not know whether to accept a message ID, an authorization ID, a command type, or a trusted boolean, nor when “current” expires after clarification, retry, reconnect, or resume. The spine precisely models consequential approval but leaves the lower compute-authority handshake informal.

- **Canonical hashing is undefined at every boundary that depends on exact equality.** An approval/idempotency epic can hash Pydantic JSON serialized with sorted keys and `exclude_none=True`, preserving binary float spelling. A promotion/persistence epic can reconstruct PostgreSQL `jsonb`, include explicit nulls, normalize `1.0` to `1`, normalize Unicode, and hash a structured consequence object rather than the localized rendered summary. Both honestly implement a “canonical body hash,” “normalized parameter hash,” and “consequence-summary hash” under AD-8/AD-10. Valid approvals and idempotent replays then fail as mismatches, or semantically different requests collide after over-normalization. The spine needs one normative canonicalization algorithm and typed hash domain for command bodies, parameters, summaries, evidence sets, policy inputs, and content-addressed S3 objects, including number precision, time form, Unicode, omitted/default/null fields, array/set ordering, schema version, and domain-separation prefixes.

- **Evidence references identify the right facts without having a common identity or resolver contract.** A run/evidence epic can store a relational UUID reference whose row contains the full AD-11 tuple and points to one S3 manifest. A provenance epic can serialize the tuple itself into a signed/encoded application URI or content hash and resolve it without an intermediate row. Both identify scenario version, producing/baseline run or schedule, group, record, and optional field/time range; neither retargets. Their OpenAPI field type, database foreign keys, evidence-link URLs, authorization loader, audit payload, and deep-link behavior are incompatible. The spine needs one evidence-reference DTO/URI grammar, namespace rules for group and record IDs, cardinality and nullability for producing-versus-baseline versions, resolver behavior, and distinction between the logical reference, `EvidenceSnapshot`, and S3 object version/checksum.

- **Evidence snapshot granularity and ownership remain open despite calling it a site-owned aggregate.** A run epic can create one snapshot manifest per schedule run containing inputs, solver configuration, result, and calculators, including infeasible/timed-out runs with no schedule version. A comparison epic can create independent immutable snapshots per calculator/evidence group and associate them with two schedule versions. Both fit AD-11/AD-12 and the many-to-many diagram. Approval/provenance code then cannot know whether it binds one snapshot ID, a stable ordered set, or an evidence group query whose membership may grow. The consequence hash and historical reconstruction change depending on that choice. Define snapshot creation boundaries, aggregate contents, whether membership is itself immutable, and the exact relations from scenario version, run, schedule version, approval, and audit.

- **The authoritative provenance timeline has correlations but no causal order.** A workflow epic can use per-agent-run persisted-event sequence as the timeline order. An audit epic can write denied/stale attempt events in separate transactions and order them by `occurred_at`, while evidence/calculator work may commit under other streams. Both include all AD-12 correlation IDs and preserve append-only records. Clock ties, transaction reordering, retries, and continuation runs produce different timelines, and a provenance UI cannot deterministically interleave request, policy decision, tool result, job progress, approval, audit, and evidence creation. The spine needs either a workflow-wide causal sequence, explicit parent/causation IDs plus deterministic tie-breaking, or a declared projection algorithm. Correlation fields alone do not make FR-20 reconstructable.

- **`Last-Event-ID` is unusable without a canonical stream and cursor model.** A run-progress epic can expose `/runs/{id}/events` and use that run's monotonically increasing sequence as the SSE ID. A chat epic can expose `/conversations/{id}/events`, merge events from agent runs, jobs, approvals, and schedule runs, and use a global persisted-event row ID or composite cursor to prevent equal per-stream sequence numbers from colliding. Both replay committed monotonic events and treat SSE as non-authoritative. A browser cannot carry one `Last-Event-ID` between these interpretations, and reconnect can skip or duplicate events when multiple child streams each emit sequence `7`. AD-6/AD-13 must name the public SSE stream aggregate, cursor encoding and comparison semantics, endpoint, authorization recheck policy, retention/reset behavior, and transaction that allocates its sequence.

- **The SSE event envelope and state projection are unspecified.** One epic can emit `event: run.completed.v1`, `id: 42`, with `data` as a full resource snapshot. Another can emit a generic `activity.v1` event whose JSON has a discriminated `kind`, resource ID, version, and patch/reference. Both use versioned names, persisted events, and the AD-14 activity vocabulary. The frontend generated REST types do not define SSE, so independently built UI and backend code have no contract for timestamp, aggregate version, correlation IDs, payload version, duplicate handling, snapshot reconciliation, problem events, heartbeat frames, or whether a replayed event invalidates TanStack Query or directly updates it. Persisted delivery does not prevent wire-level incompatibility.

- **Stable worker effect keys lack a required derivation and granularity.** A job epic can deduplicate the entire solver execution with one `(agent_run_id, tool_call_id)` effect key and treat progress checkpoints as replaceable state. An event/run epic can use separate stable keys for acceptance, each progress milestone, candidate creation, evidence creation, and terminal emission. Both use database uniqueness and the current fencing epoch for commits. When combined, the coarse key rejects legitimate sub-effects, or the fine-grained implementation replays effects that the orchestrator believed were covered by one key. AD-6/AD-8 list example key families but never define the effect catalogue, key derivation, which effects must survive recomputation, or atomic relationship among checkpoint, domain mutation, audit, and emitted event.

- **Lease semantics do not define the clock, reclaim edge, or finalization race.** A worker epic can use PostgreSQL `now()` as lease-time authority and let a current-epoch worker finalize until a reclaim transaction increments the epoch. Another can expire leases from heartbeat timestamps using an injected application clock and refuse finalization once `expires_at` has passed even if no successor has reclaimed. Both persist owner, expiry, heartbeat, and monotonic fencing, and both require the current epoch. At the exact expiry boundary they produce different winners and may map the same work to `completed`, `queued`, `failed`, or `cancelled`. Tests with fake clocks and production SQL clocks will disagree. The spine needs database-clock authority, lease acquisition/reclaim SQL semantics, heartbeat/finalization ordering, attempt accounting, and the run/job transitions caused by lease loss.

- **Rolling API/worker deployments have no persisted job protocol compatibility contract.** An API epic in image N can enqueue a v2 job or capability payload as soon as its task becomes healthy, while an old worker from image N-1 remains active during ECS rolling replacement and leases that row. Both tasks use the same immutable backend image pattern for their own release and the deployment can be health-gated. “Schema-compatible rollback” does not guarantee cross-version job, event, checkpoint, or capability compatibility. One team may rely on synchronized task replacement; another may rely on versioned handlers. The result is poison jobs or stranded checkpoints during every normal deploy. AD-17 needs an N/N-1 protocol rule, worker drain/order, job-version lease filter, compatibility test, and rollback behavior for rows already produced by N.

- **The public edge topology omits the routing and caching contract required by auth and SSE.** An API epic can publish `/api/v1/...`, `/api/v1/events`, and `/auth/callback` and set its session cookie path to `/`. An infrastructure epic can route only `/api/*` to ALB, use an SPA fallback for other paths, cache GETs by default, and fail to forward `Last-Event-ID`, CSRF, `Origin`, or all required cookies. Each obeys the CloudFront/private-S3/ALB/API topology and BFF rule. Sign-in callbacks can land in the SPA, SSE can be buffered/cached, and authenticated not-found responses can be cached across users. The spine needs authoritative public path prefixes, CloudFront behaviors, cache-disabled paths, forwarded headers/cookies/query strings, SSE timeout/buffering settings, callback/origin URLs, and trusted-proxy scheme/host handling.

- **Database migration execution has two equally compliant owners.** A persistence epic can run Alembic at API/worker process startup before accepting traffic. A deployment epic can run one explicit ECS migration task in CI/CD between Terraform and service rollout. Both use Alembic, reviewed plans, health gates, and immutable images. Together they race or execute twice; separately they imply different failure recovery, IAM permissions, startup latency, and rollback order. Least-privilege application roles are also inconsistent with granting API/worker DDL. AD-17 must designate the sole migrator identity and command, serialization/locking, preflight and failure handling, expand/migrate/contract sequencing, and which release is allowed to remove old schema.

- **“Schema-compatible rollback” has no compatibility window or executable definition.** One epic can add a column, backfill it, switch reads, and drop the legacy column in its own completed migration, considering its final schema internally compatible. Another epic's rollback plan assumes the previous image can still read/write the legacy column. Both can claim health-gated deployment and rollback evidence, but rollback after the contract step fails. The spine needs an explicit N/N-1 expand-contract window across at least one deployed release, dual-read/write or backfill rules, irreversible-migration policy, database backup/restore boundary, and tests that run both current and previous API/worker images against the intermediate schema.

- **The brownfield migration offers two mutually exclusive histories without selecting one.** The structural seed permits either migrating mutable fixture paths, `overrides` JSON, run results, and cached insights into governed immutable records or labeling them `legacy-demo-only` and excluding them. A migration epic can faithfully backfill old IDs and rows into scenario/run/schedule/evidence versions; a fixture foundation epic can seed fresh governed records and leave all old routes/data behind a legacy boundary. Downstream frontend, provenance, idempotency, and redirect epics cannot know whether old deep links survive, whether IDs are reused, whether old runs appear in history, or whether an old override contributes to a baseline. This is not an implementation detail once epics are independent; the spine must select the migration disposition and define a legacy visibility/API/data-retention contract.

- **Legacy run statuses cannot be translated deterministically from the stored data.** One adapter can map `PENDING -> queued`, `RUNNING -> running`, `FAILED -> failed`, and `COMPLETED -> completed`. Another can inspect `solver_status` and map a legacy `COMPLETED/INFEASIBLE` row to `infeasible`, or `COMPLETED/UNKNOWN` to `timed_out` when elapsed time reached the limit. Both use the permitted compatibility adapter and never expose both vocabularies. Historic rows do not retain enough reason/budget/cancellation evidence to distinguish `timed_out`, `failed/budget_exhausted`, solver unknown, or interrupted work, so the chosen mapping changes terminal payload invariants and candidate promotability. The spine needs a normative mapping table including lossy/unknown cases, a legacy terminal reason, and a decision on whether translated runs are eligible for evidence, comparison, or promotion.

- **RFC 7807 is selected without an application error registry.** An auth epic can define `resource_not_found`, `forbidden`, and `membership_inactive`; a run epic can define `run_missing`, `stale_version`, and `invalid_transition`; an approval epic can independently choose `approval_stale`, `approval_mismatch`, and `conflict`. Every code is stable inside its epic, all responses are problem details, and cross-site absence can still resemble not-found. The shared frontend cannot implement generic refresh, sign-in, retry, evidence navigation, or stale-version handling when status, code, `resource_id`, `current_version`, and retryability differ by endpoint. AD-13 needs a central error-code registry, required extensions per category, HTTP mapping, disclosure policy, and ownership/change process.

- **“Versioned REST/JSON” does not select a versioning strategy.** A foundation/API epic can expose `/api/v1` and keep schema versions out of payloads; an agent/SSE epic can keep stable URLs and version media types/event names; a capability epic can include contract version fields inside commands. All are versioned contracts and can generate OpenAPI endpoint types. Infrastructure routing, cookie paths, frontend base URLs, deprecation behavior, idempotency operation names, and problem-type URIs become inconsistent. The spine needs one public API versioning convention and a separate, explicit rule for event/capability/persisted-payload versions.

- **Idempotent replay has no canonical stored-result semantics.** A command epic can persist and replay the original HTTP status/body snapshot, ensuring byte-stable results. A domain epic can persist only the created resource/effect ID and re-read it on replay, returning the current representation and version as the “original semantic result.” Both satisfy AD-8 in ordinary cases. After later state transitions, deletion/retention, or permission change, one reveals the historical response while the other returns changed data or not-found; their OpenAPI and audit outcomes diverge. The spine must define what is stored, whether authorization is rechecked on replay, which headers/status are reproduced, how failures are cached, retention, and behavior when the original resource is no longer visible.

## Disposition

The spine should not be handed to independently implemented epics yet. Closing these holes does not require turning it into a full low-level design, but it does require a compact set of normative shared contracts: canonical DTOs and hashes; aggregate ownership/cardinalities; complete transition tables and cross-machine choreography; an atomicity matrix; site/RLS/worker authority rules; capability and job version protocols; evidence/SSE identifiers and envelopes; deployment/migration compatibility rules; and central error/API-version registries. Without those, integration will decide product authority and history accidentally in adapters and migrations—the outcome the ADs are intended to prevent.
