# Adversarial Convergence Verification

**Target:** updated `ARCHITECTURE-SPINE.md`  
**Scope:** Only the five previously blocking areas: separate workflow state/candidate creation, RLS bootstrap/leasing, normative contract minimums, S3-before-PostgreSQL evidence ordering, and cutover/rolling compatibility.

**Verdict:** **FAIL — four concrete convergence holes remain.**

- **The candidate lifecycle is now singular, but approval choreography is not closed.** AD-10 and AD-22 now agree that feasible solver completion creates the candidate and promotion only points the baseline at that existing version. The separate graphs still permit incompatible approval implementations: `ApprovalRequest` has `pending -> approved -> consumed`, but no transition from `approved` to `stale` or `expired` when AD-10's promotion-time revalidation fails after the decision; `AgentRun` resumes on “decision recorded” without saying whether that occurs before or only after atomic consumption/promotion. One epic can persist `approved`, resume the agent, then attempt promotion; another can approve and consume inside the promotion transaction. Both follow the diagrams, but they disagree on the observable state and recovery path when baseline/policy/expiry changes between approval and consumption. Fix whether `approved` is transaction-local or durably observable, add the post-decision failure transitions if it is durable, and bind the corresponding `AgentRun` transition to the same atomic bundle.

- **The RLS bootstrap functions still lack an executable privilege model.** AD-23 correctly introduces `auth.resolve_session` and `workflow.lease_next_job`, but every tenant table is forced behind site RLS while the caller knows no site yet. `auth.resolve_session` is declared `SECURITY DEFINER`, but the function-owner role and its narrowly scoped RLS-bypass/table privileges are not fixed; a normal/table-owner role remains subject to `FORCE ROW LEVEL SECURITY`. More directly, `workflow.lease_next_job` is not declared `SECURITY DEFINER` at all, so the `NOBYPASSRLS` lease role cannot scan cross-site jobs before receiving the returned site context. Independent persistence and worker epics can therefore choose incompatible privileged owners or build a lease function that returns no rows. Require both functions to be hardened `SECURITY DEFINER`, specify dedicated non-login owners and exact grants/revokes, and define the audited predicates each may bypass.

- **The normative minimums still leave the original shared schedule/activity shape fork open.** The new table is a useful field inventory, but entries such as `ScheduleVersionV1` still say only “immutable assignments, metrics, objective components,” `ScenarioProjectionV1` names collections without element shapes, and `ActivityItemV1` has an unconstrained “planner-visible payload” whose discriminants are prose categories rather than a literal tagged union. A scheduling epic can emit brownfield-style `contact_id/task_id/start_h/end_h` assignment rows while comparison/frontend epics use worker IDs and integer-minute interval objects; both satisfy the listed minimum. Since these are the very nested values exchanged across epics, compatibility cannot be delegated to later schema files without making their publication a predecessor gate. Fix the nested row/union schemas here or require the complete checked-in schema fixture set to land and pass compatibility tests before any consuming epic begins.

- **Cutover ordering is now safe before governed work, but post-contraction rollback can still rewind authoritative history.** AD-25's maintenance-window sequence closes the frontend/API split and performs the one-way cutover before governed durable work exists. AD-24 retains a destructive contraction as soon as old tasks are gone, then says an incompatible rollback uses database restore. A fault discovered after contraction can therefore force restoration to an earlier database point and discard accepted messages, approvals, promotions, or audit events, contradicting their durable/authoritative status. “N and N-1 remain compatible during rolling replacement” does not define a post-deploy rollback window. Keep the prior image/schema compatible for a declared rollback period before contraction, treat contraction as a later separately gated release, and require forward-fix or point-in-time recovery with quiescence/reconciliation rather than ordinary rollback that silently loses committed work.
