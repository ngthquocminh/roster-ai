# Final Adversarial Independent-Epic Compatibility Review

**Target:** updated `ARCHITECTURE-SPINE.md`  
**Method:** Re-run the prior A/B implementation attacks against the added AD-20 through AD-25 and the amended persistence, state, deployment, and migration rules. A hole remains when two independently implemented epics can follow the written rules literally and still disagree at merge or runtime.

**Verdict:** **FAIL — materially improved, but still not an executable independent-epic contract.** The update closes the broad choice of canonical JSON, scheduling time units, an SSE envelope/cursor form, aggregate-owner names, direct tenant keys, mixed-version intent, and the legacy-history disposition. It also introduces direct contradictions and leaves several named “V1” schemas and deployment/security protocols undefined, so independent teams can still produce incompatible systems.

## What the update successfully closed

- **The legacy-history fork is closed.** AD-25 selects exclusion rather than allowing each epic to decide between backfill and legacy-only history, removes the commit-then-thread worker path, and makes lowercase V1 status cutover coordinated. The prior ambiguous mapping of `COMPLETED/UNKNOWN/INFEASIBLE` no longer needs to become governed history.

- **The gross time/hash/SSE choices are closed, but not their input semantics.** AD-20 chooses integer-minute half-open scheduling offsets, UTC horizon start, IANA site timezone, SHA-256, and RFC 8785. AD-21 chooses an event envelope, cursor syntax, replay comparison, and heartbeat/proxy behavior. These choices eliminate several byte- and transport-level forks from the first review.

- **Aggregate and deployment direction are substantially clearer.** AD-22 assigns aggregate owners and names atomic bundles; AD-23 requires direct `site_id`, forced RLS, separate migration/runtime roles, and create-only evidence; AD-24 selects expand-migrate-contract with N/N-1 rolling compatibility. These are real improvements, though the remaining findings show where the new rules are contradictory or not yet implementable.

## Remaining findings

- **AD-7 and AD-22 define incompatible meanings for a schedule run.** AD-7's only legal graph sends `running -> approval_required -> running` when an exact action is proposed and decided. AD-22's `complete-compute` bundle makes the run terminal and creates its schedule version before `request-approval`; its promotion bundle then operates after that terminal completion. A scheduling epic following AD-22 will set the run to immutable `completed`, while a run-status/UI epic following AD-7 will reject the later approval request because terminal states cannot transition to `approval_required`. The PRD also says a completed candidate remains separate until approval. The spine needs separate, explicitly named graphs for `ScheduleRun`, `AgentRun`, `Job`, and `ApprovalRequest`; the current overloaded word “run” makes literal compliance impossible.

- **AD-10 and AD-22 disagree about when the schedule version is created.** AD-10 says promotion commits the baseline pointer, **schedule version**, approval decision, and audit in one transaction. AD-22 says `complete-compute` creates the schedule version, while `promote-baseline` contains only approval decision, baseline pointer, audit, and event. An approval epic following AD-10 can clone/create a promoted schedule version; a worker epic following AD-22 creates the candidate version at completion and expects promotion only to point at it. They will bind approval to different IDs and produce different evidence ownership. Amend AD-10 to say whether promotion references an existing immutable candidate or creates a distinct promoted derivative, then make the bundle list identical.

- **The baseline pointer still lacks a cardinality and key.** AD-9 and AD-22 name a site baseline pointer, but neither the ER diagram nor contract list specifies whether there is exactly one pointer per site or one site-owned pointer per `(site, scenario)`. A governance epic can put `baseline_schedule_version_id` on `site`; a scenario epic can create `site_baseline(site_id, scenario_id, ...)`. Both are site-owned, versioned pointers. Fixture switching, expected baseline version, cross-scenario comparison, promotion uniqueness, and the optimistic-lock resource remain incompatible. Naming an aggregate without defining its identity did not close the prior ownership hole.

- **Conversation-to-scenario ownership remains undefined.** One conversation epic can bind a conversation permanently to one immutable `scenario_version`; another can bind each agent run/proposal to an explicit scenario and allow one durable conversation to move between catalogue scenarios. Both satisfy AD-4, AD-9, AD-14, and the owner table. They disagree on database keys, authorization loading, chat return links, activity projection, and what “selected scenario” means when reopening a conversation. `ScenarioProjectionV1` does not answer which aggregate owns selection or whether it can change.

- **The manual deterministic path still has no valid correlation shape.** AD-15 allows manual solver execution without `AgentRuntime`; AD-12 says every audit/provenance envelope carries agent-run and tool IDs; the ER diagram relates every job/event to an agent run; AD-22 assigns jobs/events to workflow but does not state whether those relationships are optional. A manual-run epic can manufacture a synthetic agent run/tool call, while an audit epic can make those fields nullable and distinguish `initiator_type=manual`. Both retain all authority and durability guarantees. Their foreign keys, `AuditEnvelopeV1`, event correlation, provenance UI, and budget accounting conflict. The contracts need an explicit initiator union and required/nullable correlation matrix.

- **AD-20 names schemas without defining most of them, and it omits the most shared schedule schema.** The document lists `ProposalV1`, `ApprovalBindingV1`, `ActivityItemV1`, and others, but gives no field/type/nullability/cardinality definitions or schema source checked into the artifact; `ScheduleVersionV1`, assignment rows, metrics, capability descriptors, job envelopes, and checkpoints are not listed at all. A run epic can preserve the brownfield `contact_id/task_id/start_h` vocabulary behind its adapter while a comparison epic expects worker/task/interval-minute assignment IDs and decimal money. Both can claim application-owned V1 DTOs until one implementation happens to land first. A contract name plus “compatibility tests gate change” is a dependency declaration, not a shared contract for parallel implementation.

- **Naive fixture time still admits two different immutable histories.** AD-20 defines the target representation but never says how current naive source timestamps such as `2026-06-01T00:00:00` become `horizon_start`. An importer can interpret them as site-local civil time using `site_timezone`; another can treat them as UTC because storage is UTC. Both then produce valid UTC horizon starts and integer-minute offsets. Scenario checksums, day labels, evidence ranges, schedules, and approval hashes differ by the UTC offset. The import contract must fix source timezone interpretation, DST ambiguity/nonexistence handling, and reject-versus-round behavior for non-minute source precision.

- **“Scenario checksum” does not define what is checksummed.** AD-20 requires the checksum in `RunSnapshotV1`, and AD-25 imports “checksummed fixture files.” A seeding epic can hash the raw fixture bytes; another can hash RFC-8785 canonical source JSON; a scenario epic can hash the normalized `ScenarioProjectionV1`. All are checksummed, immutable imports, but whitespace/key order changes create a new version only in the first, while importer/default/normalization changes create a new version only in the third. Runs and evidence cannot independently agree what checksum proves. Define the hash domain and whether source-byte, normalized-input, and projection hashes are separate fields.

- **RFC 8785 fixes JSON bytes but not semantic normalization.** AD-8 still asks for a canonical **body** hash, while AD-10 asks for normalized parameter and consequence-summary hashes. One endpoint epic can hash the validated DTO after defaults and omission normalization; another can hash the submitted JSON exactly after RFC-8785 canonicalization. Omitted default versus explicit default, absent versus `null`, enum aliases, normalized IDs, and rendered summary text then yield different idempotency/approval results despite using the same algorithm. `ApprovalBindingV1` is named but not specified, and no rule says which typed value is hashed for each purpose or whether the schema/version is inside the domain-separated bytes rather than merely stored beside the digest.

- **The public SSE stream aggregate is still unspecified.** AD-21 says `Last-Event-ID` must match “the URL stream,” but never says whether the browser connects to a conversation, agent run, schedule run, site activity, or workflow stream. A run epic can expose one stream per schedule run; a chat epic needs a conversation feed that interleaves messages, multiple agent runs, jobs, approvals, and terminal outcomes. Both can emit valid `<stream_uuid>:<sequence>` cursors and replay greater sequences, yet a conversation client cannot merge child streams without inventing a second ordering/cursor protocol. Define the public endpoint and stream identity, which transaction allocates its sequence, and how child aggregate events project into it.

- **`ActivityItemV1` remains an unenforced wire union.** AD-14 enumerates activity kinds and AD-21 puts one typed item in every event, but the actual discriminants, payload fields, resource-version meaning, and compatibility behavior are absent. OpenAPI does not automatically describe SSE, so an SSE epic can serialize full snapshots while a frontend epic expects lightweight references that invalidate TanStack Query. Both use the named V1 envelope. Specify the JSON Schema/discriminator, REST/SSE schema-generation path, unknown-variant behavior, duplicate handling, and whether replayed events update cache directly or trigger resource refetch.

- **Authentication cannot bootstrap forced tenant RLS as written.** AD-23 says every tenant table—including session/membership under the owner table—carries `site_id`, forces RLS, and is read using transaction-local trusted actor/site context. AD-3 says the BFF receives only an opaque session ID and must resolve current actor/site from the session and membership. Before reading the session, the BFF does not yet know the site value required to set RLS. One identity epic can use a privileged/security-definer session resolver; another can put a site hint in the cookie and use it only to establish the RLS predicate before verifying membership. Both can claim final authority is server-derived, but their threat model and database roles differ. The spine must define a non-tenant authentication bootstrap relation/function and its exact privilege boundary.

- **Global worker lease discovery remains incompatible with forced site RLS.** Every job is tenant-scoped and forced behind a transaction-local site predicate, yet a general worker must discover a leaseable row before it knows that row's site. `FOR UPDATE SKIP LOCKED` solves concurrency, not authorization/bootstrap. One worker epic can loop over configured sites and set context for each; another can use a constrained bypass-RLS/security-definer lease function that returns site plus epoch. Both are plausible under AD-3/AD-23, but they require different runtime roles, repository APIs, fairness, and scaling semantics. The one-user MVP conceals the conflict; the architecture claims future pooled isolation. Select the lease-discovery authority explicitly.

- **The audit uniqueness keys suppress legitimate distinct attempts.** AD-12 makes denied/stale/failed/cancelled attempts unique on `(site_id, request_id, outcome)`. One planner request can produce two denied tool calls, a stale approval followed by a stale promotion attempt, or multiple consequential actions with the same outcome. An audit epic enforcing the literal key will drop all but one, violating FR-21's complete audit; an orchestration epic that assigns a new request ID per tool/action will fragment the single request correlation and disagree with HTTP idempotency. The key must include a canonical attempt/effect/action identifier, and the contract must distinguish transport request, command attempt, tool call, approval decision, and worker effect IDs.

- **The complete-compute “atomic bundle” crosses PostgreSQL and S3 without a protocol.** AD-22 groups terminal run, schedule version, evidence references, and event; AD-12/AD-23 place large evidence in create-only S3. A worker epic can upload S3 first and then commit the database bundle, leaving harmless but permanent orphan objects on transaction failure. Another can commit the DB reference first and upload afterward, temporarily or permanently creating dangling authoritative evidence on crash. Neither can make both stores atomic, and AD-17 explicitly forbids in-product deletion. Define the only allowed order, pending/verified snapshot states, checksum verification, retry/reconciliation job, and whether a run may become terminal before every referenced object is durably readable.

- **Job, checkpoint, lease, and effect contracts are still absent.** AD-6 names lease fields and fencing; AD-23 adds `SKIP LOCKED`; neither supplies a job state graph, payload/schema version, checkpoint codec, handler identity, attempt accounting, database-clock rule, heartbeat/finalization SQL semantics, or effect-key derivation. A workflow epic can deduplicate one whole tool execution with `(agent_run_id, tool_call_id)` while a run/evidence epic uses separate stable keys for candidate, snapshot, audit, and terminal event. Both satisfy the example key rule but collide or duplicate when composed. `RunSnapshotV1` also omits job ID/fencing epoch, so the complete-compute orchestrator has no normative input proving current lease authority.

- **Capability modules still lack a common descriptor and persisted-version lifecycle.** AD-5 enumerates descriptor properties, but AD-20 does not define `CapabilityDescriptorV1`, capability identity, registry discovery, job/tool payload versions, or checkpoint compatibility. One module epic can register `scheduling.compare.v2` as a versioned dispatch name; another runtime can expose stable `scheduling.compare` and load the current handler with upcasters. Both declare version semantics. Queued work and resumed agent runs fail during deployment or module removal because AD-24's generic N/N-1 rule does not say which handlers must remain installed or how workers filter unsupported job versions. Define registry source, stable identity, version negotiation/upcasting, and unavailable-version terminal behavior.

- **Compute authority still has no exact persisted binding.** AD-5 says compute needs the planner's “current explicit run request,” but no contract defines current, its ID, expiry, scope, one-time/retry behavior, or relation to proposal/baseline versions. A chat epic can treat an explicit message/activity item as authority; a manual API epic can create a one-time run-authorization record. Both keep authority outside the model. The capability gateway cannot independently accept both, and reconnect/clarification/retry semantics diverge. Consequential approval is exact and persisted; compute authorization needs a smaller but equally explicit application-owned binding.

- **Approval itself still lacks a state graph and race semantics.** AD-10 calls it a one-time persisted state machine but gives no states/transitions, and AD-7 incorrectly folds approval into the run graph. One approval epic can expire lazily when a decision is attempted; another can have a worker transition pending requests to expired. At the exact expiry instant, one can accept a decision whose transaction began before expiry while the other rejects unless it commits before expiry. Rejection, expiry, policy invalidation, baseline staleness, and replay have different audit/event results. Add the approval graph, database-clock comparison, CAS predicates, and mapping into agent/workflow state.

- **Application transaction composition is still not defined beneath the bundle names.** AD-22 says only an application orchestrator crosses owners and repositories may not widen a bundle, while the convention says tools call use cases and command handlers own unit-of-work boundaries. A capability use case can still open and commit its own command transaction inside an agent orchestrator that expects the tool-call/effect/event bundle to be atomic. Alternatively, the outer orchestrator can hold a transaction across a model, solver, or S3 call. Both can point to the written rules. State explicitly that remote/CPU/object-store work never occurs inside a database transaction, which orchestrator creates each unit of work, and whether nested use cases must join, return intents, or are forbidden from opening transactions.

- **AD-24's rollback escape contradicts durable-work and audit continuity.** It allows rollback to N-1 only while schema-compatible and otherwise prescribes a tested database restore. Restoring an earlier backup after N accepted messages, approvals, promotions, or audit events discards authoritative committed work, violating AD-6 and AD-12. An infrastructure epic can implement restore as written; an application epic will assume committed acknowledgements and audit are never rewound. Expand-contract should keep N-1 rollback possible for an explicit post-deploy window, or define a forward-fix/point-in-time recovery protocol with quiescence, reconciliation, and declared data-loss boundary; “restore” is not a safe ordinary deployment rollback.

- **The N/N-1 compatibility rule is not tied to persisted protocols or a duration.** An API N task may enqueue a new capability/job/event/checkpoint payload while worker N-1 is still leasing; AD-24 declares compatibility but does not require a version filter, supported schema set, producer downgrade, or compatibility suite covering those records. Destructive contraction may begin as soon as old tasks are gone, immediately eliminating later image rollback even though health-gated rollback is a stated feature. Define the compatibility matrix for database schema plus every persisted V1 payload, worker drain/order, minimum rollback window, and proof that N-1 can process or safely skip every row N can create.

- **The public path and API-version strategy remain open.** AD-13 says versioned REST/JSON; AD-20 names V1 schemas; AD-21 refers to URL streams and CloudFront “auth/API/SSE” behaviors, but no authoritative prefixes or versioning strategy exist. An API epic can publish `/api/v1` and `/api/v1/conversations/{id}/events`; infrastructure can route `/api/*` plus `/events/*`, while identity uses `/auth/callback`. All satisfy the topology in prose and still misroute callbacks or apply caching/buffering rules to the wrong paths. Fix the public path table, callback/origin URLs, cookie paths, and whether versions live in URLs, media types, or payloads.

- **`ProblemDetailsV1` is named without a shared error registry.** Independent identity, workflow, evidence, and approval epics can each choose stable codes and decide when `resource_id`, `current_version`, or retry metadata is present. Every response remains valid RFC 7807 and structurally V1, but the frontend cannot implement uniform refresh, conflict recovery, not-found nondisclosure, or reauthentication. Define the code enum/namespace, HTTP mapping, required extensions by category, disclosure rules, retryability, and ownership/change process.

- **Idempotent replay semantics are unchanged.** AD-8 still says “original semantic result” without saying whether the idempotency record stores the original HTTP status/body or only the effect/resource ID. One epic can replay a byte-stable historical response; another can re-read the current resource and serialize its latest version. Both are defensible semantic replays. After state changes, permission changes, or retention, they return different status, versions, and disclosure. Specify stored result fields, authorization recheck, error caching, retention, and behavior when the resource is no longer visible.

- **The one-way cutover is selected but not failure-atomic with deployment.** AD-25 coordinates fixture import, OpenAPI regeneration, route/status cutover, and removal of the old executor, but does not order those steps against AD-24's database migration, API/worker rollout, or rollback. A database epic can import fixtures before image deployment; a frontend epic can ship generated V1 routes with the SPA before the API is ready; an infrastructure epic can roll back only one tier. Each follows its assigned rule, yet the portfolio can expose no usable history or a frontend/API contract mismatch. Define a cutover state/feature gate, idempotent seeding identity, readiness check, tier order, and rollback behavior that never re-exposes the prohibited legacy history.

## Disposition

Do not release the spine to independently executed epics until the contradictions in AD-7/AD-10/AD-22 are resolved and the remaining named contracts become actual normative schemas/protocols. The shortest credible closure is: split state graphs by aggregate; make candidate creation/promotion lifecycle singular; define baseline and conversation/scenario keys; publish concrete JSON Schemas for schedule/activity/approval/job/capability/problem contracts; fix session and worker RLS bootstrap; specify S3/PostgreSQL evidence choreography; and turn AD-24/AD-25 into an executable rollout and rollback sequence.
