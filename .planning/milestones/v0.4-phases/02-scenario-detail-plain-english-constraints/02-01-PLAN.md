<objective>
Add the one backend change this phase requires: a read path exposing a scenario's persisted overrides over HTTP (D-01), and persistence of the human-readable `parsed_constraint` echo alongside the stored `{tool, args}` (D-02). This unblocks SCEN-03 criterion 1 ("see **every** override currently applied") — today no HTTP path returns a scenario's stored overrides — and CONS-02's fidelity requirement (a reloaded override reads identically to a freshly-applied one).

Purpose: The Editor loads the full override list on mount and it survives reload; the reloaded form is the persisted readable sentence, never raw tool-call JSON.
Output: `GET /scenarios/{scenario_id}/overrides` → `list[OverrideOut]`; `parsed_constraint` persisted; `docs/API.md` updated in lockstep; backend contract tests.

Decision (Claude's Discretion, RESEARCH Open Question 1 / Pitfall 3): the endpoint returns overrides in the stored dict's natural insertion order (first-applied-first), stable across idempotent re-applies, with NO server-side re-sort. This is the zero-extra-code choice and is documented here as deliberate.

Decision (Claude's Discretion, D-01 shape): dedicated endpoint `GET /scenarios/{scenario_id}/overrides` (Option B), NOT a field on `ScenarioOut` (Option A). Rationale: the approved UI-SPEC (E1/E2) requires the scenario-detail fetch and the overrides fetch to resolve and error **independently**, which is only physically achievable as a second HTTP call; Option A would also silently change `GET /scenarios`' already-shipped (SCEN-01) list-row shape (RESEARCH Summary + Pitfall 1).

Decision (Claude's Discretion, legacy migration): graceful-fallback via `OverrideOut.parsed_constraint: str | None = None`, NOT backfill. Backfill would require extracting/duplicating the six per-tool string templates and re-loading each scenario's fixture to re-resolve GUIDs to names (RESEARCH Pitfall 6) — real engineering for near-zero value on local dev DBs.
</objective>
