## User Constraints (from CONTEXT.md)

### Locked Decisions

Four gray areas were surfaced and decided by the user. The central one (D-01)
carries a scope consequence: it adds a second backend change to a milestone that
scoped BE-01/CORS as the *only* backend change. The user chose it knowingly
because criterion 1 ("see **every** override currently applied") cannot otherwise
be met — there is no HTTP path today that returns a scenario's stored overrides.

**Applied-overrides source (SCEN-03, criterion 1)**
- **D-01:** **Add a backend read path** that exposes a scenario's persisted
  overrides over HTTP. Today `ScenarioOut` (`backend/api/schemas.py:15`) omits
  overrides entirely and the `overrides` JSON column is never read back over the
  API — so `POST /constraints`'s `applied[]` is the *only* place override data
  reaches the client, which cannot show pre-existing overrides on open/reload.
  The read path fixes that: the Editor loads the full override list on mount and
  it survives reload. Shape (endpoint vs adding an `overrides` field to
  `ScenarioOut`) is the planner's call — either satisfies the requirement; a new
  field on `ScenarioOut` is the smaller diff, a dedicated `GET
  /scenarios/{id}/overrides` keeps `ScenarioOut` lean. **`docs/API.md` and the
  generated `schema.d.ts` must be updated in lockstep** with whatever shape is
  chosen (this repo has a documented history of doc/code drift — see Phase 1
  context D, commit `93ca4e0`).

**Override display fidelity (CONS-02)**
- **D-02:** **Persist `parsed_constraint` alongside `{tool, args}`** in the
  scenario's `overrides` column. Currently the column stores only `{tool, args}`
  (confirmed in `constraint_service.py` and `insight_service.py:161`) — the
  human-readable echo is generated by the parser, returned in the `POST
  /constraints` response, then discarded on persist. Persisting it means a
  reloaded override reads **identically** to a freshly-applied one; one render
  path, one appearance, always readable. Rejected alternatives: humanizing
  `{tool, args}` in TypeScript (duplicates parser phrasing → drift risk; client
  only has the task *id* `T123`, not the name "Pick"), and accepting two
  fidelities (same override visibly changes after reload; reloaded form is the
  "raw tool-call JSON" CONS-02 forbids).
  - **Migration note for the planner:** existing scenarios may already have
    overrides stored *without* `parsed_constraint` (the pre-D-02 shape). The read
    path must degrade gracefully for those legacy entries (e.g. fall back to a
    tool+args rendering, or backfill) rather than assuming the field is always
    present.

**Constraint box interaction model (CONS-01, CONS-04)**
- **D-03:** **Running transcript.** Keep a session log of each submission and its
  parse outcome (chat-like), rendered **above** the durable applied-overrides
  list. This makes the clarification-and-rephrase flow (criterion 4, "rephrase
  without losing their place") natural — the question stays in the transcript and
  the user re-submits. The transcript is **session-only** (not persisted); the
  overrides list (D-01) is the durable record. The transcript shows *attempts and
  outcomes*; the overrides list shows *what is currently applied*.

**Outcome-state rendering (CONS-03, CONS-04, CONS-05)**
- **D-04:** **Four fully distinct treatments**, because one `POST /constraints`
  `200` can carry several of these at once and criterion 5 explicitly requires
  the provider-down state be visibly distinct from "invalid constraint":
  1. **`applied[]`** — added to the overrides list (and echoed in the transcript).
  2. **`rejected[]`** — per-item **inline** reason + valid options (the backend's
     `error` string already carries plain-English guidance, e.g. "factor must be
     positive, got -1. Use a value > 0…").
  3. **`clarification_needed`** (a `200` field, string|null) — shown as a question
     that invites a rephrase; user's text is not lost.
  4. **`503` provider-down** — a distinct banner ("the provider is unavailable"),
     **not** styled like a validation error.
  - **D-05:** Also handle the fifth outcome: **`no_constraint_found: true`** — a
    neutral "no constraint was recognized in that text" message (not an error, not
    a success). This is a real response field, not an edge case to ignore.

### Claude's Discretion (planner decides; not pre-answered)
- Exact backend shape for D-01 (field-on-`ScenarioOut` vs dedicated endpoint).
- Backfill vs graceful-fallback strategy for legacy overrides missing
  `parsed_constraint` (D-02 migration note).
- Visual layout of the transcript-above-overrides Editor (D-03) within the
  existing shadcn/ui + Tailwind system.
- Whether the overrides read uses its own TanStack Query key or extends the
  existing scenario-detail query; invalidation on successful apply.

### Deferred Ideas (OUT OF SCOPE)
- **Override deletion / editing** — not in any Phase 2 criterion, and no `DELETE`
  path for overrides exists in the backend. Overrides accumulate; removing one is
  a future capability (its own phase), not this one.
- **Seeing an override's effect on the schedule** — Phase 3 (run trigger +
  polling). `POST /constraints` deliberately does not solve.

## Summary

This phase is almost entirely frontend work against endpoints that already exist and are already tested (`POST /constraints`, fully covered by `backend/tests/test_constraints_api.py`). The one piece of new backend surface — a read path for a scenario's persisted overrides (D-01) — is a small, well-contained addition to `backend/api/schemas.py` and `backend/api/routers/scenarios.py`, plus a one-line change in `backend/services/constraint_service.py` to persist `parsed_constraint` (D-02).

The single most load-bearing research finding is a cross-reference between the (already-approved) `02-UI-SPEC.md` and D-01's "planner's call" framing: UI-SPEC's E1/E2 loading-state rows state the scenario-detail fetch and the overrides fetch resolve **independently** ("D-01's read is its own call") and error **independently** ("mirrors Phase 1 Home's dual-independent-query banner precedent"). That is only physically achievable if D-01 is implemented as a **second HTTP call** — i.e. a dedicated `GET /scenarios/{scenario_id}/overrides` endpoint (Option B), not a field folded into the existing `ScenarioOut` (Option A), which is one call and cannot resolve/error independently of itself. CONTEXT.md frames the choice as open ("the planner's call"); UI-SPEC — approved after CONTEXT.md, and describing the *rendered result* it says is "agnostic" to the HTTP shape — nonetheless bakes in an assumption that only Option B satisfies. This isn't a re-litigation of Claude's Discretion; it's a technical fact connecting two already-locked artifacts that the planner needs surfaced.

Everything else is a straightforward application of Phase 1's established patterns: typed `openapi-fetch` wrappers derived via indexed access into generated `paths`, TanStack Query hooks with an invalidation contract between a mutation and a list query, and the `ErrorBanner`/status-branching conventions already proven in `CreateScenarioDialog`.

**Primary recommendation:** Implement D-01 as `GET /scenarios/{scenario_id}/overrides` returning `list[OverrideOut]` (bare array, matching `GET /scenarios`' and `GET /fixtures`' existing convention), with `OverrideOut.parsed_constraint: str | None = None` so legacy entries (pre-D-02) deserialize without a FastAPI 500. Persist `parsed_constraint` via a one-line addition in `constraint_service.py`'s existing read-modify-write. On the frontend, fetch the two Editor queries as TanStack Query hooks with the overrides query `enabled` on the scenario query's success (dependent-but-independently-loading), and invalidate the overrides query key in the constraint-apply mutation's `onSuccess`.

### Pattern 1: Typed endpoint wrapper via indexed access (established, Phase 1)
**What:** Every request/response type is derived from the generated `paths` type via indexed access — never hand-authored.
**When to use:** Every new endpoint wrapper this phase (`getScenario`, `getScenarioOverrides`, `applyConstraint`).
**Example:**
```typescript
// Source: frontend/src/api/scenarios.ts (existing pattern, Phase 1)
type CreateScenarioBody = paths["/scenarios"]["post"]["requestBody"]["content"]["application/json"];

export async function createScenario(body: ...) {
  const { data, error, response } = await client.POST("/scenarios", { body });
  if (error) {
    // T-1-02: attach HTTP status so callers can branch without displaying backend internals
    throw { status: response.status, ...error };
  }
  return data;
}
```
Applied to this phase's `applyConstraint`:
```typescript
// frontend/src/api/constraints.ts (new file, same pattern)
import { client } from "./client";
import type { paths } from "./schema";

type ConstraintParseRequest =
  paths["/constraints"]["post"]["requestBody"]["content"]["application/json"];

export async function applyConstraint(body: ConstraintParseRequest) {
  const { data, error, response } = await client.POST("/constraints", { body });
  if (error) {
    // CONS-05 needs response.status to distinguish 503 (provider down) from 422 (validation)
    throw { status: response.status, ...error };
  }
  return data; // ConstraintParseResponse: applied[], rejected[], clarification_needed, no_constraint_found
}
```

### Pattern 2: TanStack Query invalidation on mutation success (established, Phase 1 + verified against official docs)
**What:** A mutation invalidates a specific query key so the dependent list refetches; no manual cache write, no optimistic insert.
**When to use:** `useApplyConstraint`'s `onSuccess` must invalidate the overrides query key so newly `applied[]` overrides appear in the list (criterion 2).
**Example:**
```typescript
// Source: https://github.com/tanstack/query/blob/v5.90.3/docs/framework/react/guides/invalidations-from-mutations.md
const mutation = useMutation({
  mutationFn: addTodo,
  onSuccess: async () => {
    await queryClient.invalidateQueries({ queryKey: ['todos'] })
  },
})
```
Applied to this phase (following the exact shape of `frontend/src/hooks/useCreateScenario.ts`):
```typescript
// frontend/src/hooks/useApplyConstraint.ts
export function useApplyConstraint(scenarioId: string) {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: (text: string) => applyConstraint({ scenario_id: scenarioId, text }),
    onSuccess: () => {
      // Key MUST byte-match useOverrides' queryKey (same cross-plan-contract
      // hazard useCreateScenario.ts's comment documents for ["scenarios"]).
      queryClient.invalidateQueries({ queryKey: ["scenario", scenarioId, "overrides"] });
    },
  });
}
```
Note: `applied[]`, `rejected[]`, and `clarification_needed` all arrive in the mutation's resolved data too — the transcript append happens in the calling component's own `onSuccess` callback passed to `.mutate()`, not inside this hook (mirrors `CreateScenarioDialog`'s `createScenario.mutate(body, { onSuccess: ... })` two-level pattern), since the transcript is component/session state, not query cache.

### Pattern 3: Dependent query (`enabled`) for scenario-then-overrides
**What:** The overrides query should not fire until the scenario query has confirmed the scenario exists, avoiding a race where the overrides endpoint 404s independently in a way UI-SPEC's E7 (single terminal 404 view) doesn't define a rendering for.
**When to use:** `useOverrides` hook.
**Example:**
```typescript
// frontend/src/hooks/useOverrides.ts
export function useOverrides(scenarioId: string, options: { enabled: boolean }) {
  return useQuery({
    queryKey: ["scenario", scenarioId, "overrides"],
    queryFn: () => getScenarioOverrides(scenarioId),
    enabled: options.enabled, // caller passes: scenarioQuery.isSuccess
  });
}
```
This still satisfies UI-SPEC's "the two may resolve at different times" — a dependent query still has its own independent loading/populated/error lifecycle once started; it just has a lower bound (scenario confirmed to exist first).

### Anti-Patterns to Avoid
- **Reusing `ScenarioOut` for the overrides read (Option A):** Contradicts the approved UI-SPEC's independent-loading/independent-error framing for the two Editor fetches (see Summary). Also silently changes `GET /scenarios`' (SCEN-01, Phase 1, already shipped) response shape for every scenario in the Home list, which is out of this phase's scope.
- **Reusing `AppliedConstraint` verbatim as the read-path response model:** Its `parsed_constraint: str` is non-optional; any legacy override (pre-D-02) missing the key will make Pydantic/FastAPI raise a `ResponseValidationError` (500) at serialization time, not a clean 4xx. A distinct `OverrideOut` model with `parsed_constraint: str | None = None` is required.
- **Unconditionally clearing the textarea in the mutation's `onSuccess`:** `CreateScenarioDialog`'s pattern of `onSuccess: () => onOpenChange(false)` (always-clear) does NOT transfer here — CONS-04 requires the typed text to survive every non-full-success outcome (rejected-only, clarification, no-match, 503). The clear condition must be evaluated against the *response body*, not treated as "request succeeded."
- **Branching on `error.detail` string content for 503 vs 422:** T-1-02's established convention is to branch on `response.status`, never on error message text (the same convention `CreateScenarioDialog`'s 400-vs-422 branching already uses). A 503 from `POST /constraints` and a 422 both arrive as `{"detail": "..."}` / `{"detail": [...]}` — status code is the only reliable discriminator.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Refetch overrides list after a successful constraint apply | Manual `refetch()` call chained after `mutate()`, or a manually-managed local list merged with server data | `queryClient.invalidateQueries({ queryKey: [...] })` in the mutation's `onSuccess` | Established Phase 1 contract (`useCreateScenario.ts`); avoids the "cache and server silently diverge" class of bug that an optimistic local merge risks |
| Escaping `parsed_constraint` / `error` / `clarification_needed` text before render | Any manual HTML-escaping or sanitization function | Plain JSX text-node interpolation (`{entry.parsed_constraint}`) | React's default escaping is the complete mitigation (same convention as `ScenarioTable`'s T-1-03 comment); these strings can contain user-influenced task/member names and constraint phrasing, never raw HTML |
| Distinguishing which query resolved first / avoiding a stale-overrides flash | Manual `isMounted` refs, manual request-generation counters | TanStack Query's built-in query-key-scoped caching + `enabled` dependent queries | TanStack Query already handles race conditions, cancellation, and staleness per query key; hand-rolled request tracking duplicates this and is a common source of the exact race it's meant to prevent |
| Generating request/response TypeScript types for the two new/changed endpoints | Hand-written `interface`s mirroring `docs/API.md` prose | `npm run codegen` (regenerates `schema.d.ts` from the live OpenAPI schema after the D-01 backend change) | Established Phase 1 convention; this repo has a documented drift incident (commit `93ca4e0`) specifically from hand-maintained API docs/types diverging from code |
| Humanizing legacy `{tool, args}` overrides into a full sentence client-side | A TypeScript switch statement re-implementing `constraint_service.py`'s per-tool `parsed_constraint` string templates | The UI-SPEC's fixed "Tool Label Map" + `key=value` fallback rendering (deliberately lower-fidelity, explicitly not a fabricated sentence) | CONTEXT.md D-02 already rejected this alternative explicitly: the client only has resolved GUIDs (`task_id`), not names, so any client-side humanization attempt would either be wrong or require a second lookup round-trip the spec doesn't call for |

**Key insight:** Nearly every "don't hand-roll" item in this phase reduces to the same principle already established in Phase 1: the typed client + TanStack Query pairing removes the need for hand-rolled fetching, typing, or cache-consistency code, and the backend remains the single source of truth for anything requiring domain knowledge (task/member names, constraint validity, provider availability) that the client cannot safely reconstruct.

## Common Pitfalls

### Pitfall 1: Choosing Option A (field on `ScenarioOut`) without noticing the UI-SPEC conflict
**What goes wrong:** The Editor renders both fetches as a single combined loading/error state (because there is only one query), which fails UI-SPEC E1/E2's stated independent-resolution and independent-error behavior, and silently adds overrides payload to every `GET /scenarios` list-row (Home/SCEN-01), which is untested and out of this phase's stated scope.
**Why it happens:** CONTEXT.md's D-01 prose ("a new field on ScenarioOut is the smaller diff") reads as a real endorsement if the planner doesn't cross-reference the already-approved UI-SPEC written after it.
**How to avoid:** Implement Option B (`GET /scenarios/{scenario_id}/overrides`, dedicated route, dedicated response model). See Summary and Architecture Patterns.
**Warning signs:** A single `useScenario` query object is being destructured to drive both the header and the overrides list's loading/error UI.

### Pitfall 2: FastAPI 500 on legacy overrides missing `parsed_constraint`
**What goes wrong:** If `OverrideOut.parsed_constraint` is typed as required `str` (e.g. by reusing `AppliedConstraint`), any scenario with an override persisted before this phase's D-02 change will fail Pydantic response validation, and `GET /scenarios/{id}/overrides` returns a 500 instead of a normal 200 with a null field.
**Why it happens:** `AppliedConstraint` (the `POST /constraints` response shape) was designed for the always-just-parsed case, where `parsed_constraint` is always freshly computed and therefore always present — that invariant does NOT hold for stored data written before this phase existed.
**How to avoid:** Define a distinct `OverrideOut` model: `parsed_constraint: str | None = None`. Build it with `raw_overrides[k].get("parsed_constraint")` (not `["parsed_constraint"]`) when shaping the response.
**Warning signs:** A 500 (not empty list, not 404) from the new endpoint on a scenario that has any override applied via `POST /constraints` before this phase's backend change lands — including overrides created during Phase 1/Phase 2 manual testing against a local dev DB.

### Pitfall 3: Overrides list order silently depends on Python dict insertion order
**What goes wrong:** `constraint_service.py`'s `existing[entry["id"]] = {...}` writes into a dict keyed by content-hash id; `json.dumps`/`json.loads` preserve insertion order (Python 3.7+ dicts, and JSON objects are unordered per spec but this repo's own read/write round-trip is order-preserving in practice). Re-applying an already-applied constraint (idempotent overwrite, same id) does NOT move it to the end — it keeps its original insertion position. If the planner assumes "most recently applied" ordering without verifying this, the rendered list order will be wrong for any idempotent re-submission.
**Why it happens:** It's a non-obvious property of Python's dict + `json` module behavior, not documented anywhere in the API contract (`docs/API.md`'s `ConstraintParseResponse.applied` doc is silent on ordering, since a single `POST` response's `applied[]` order is a separate, freshly-built list each call — this pitfall is specific to the **stored**, multi-call-accumulated overrides column).
**How to avoid:** Decide explicitly (this is a real open sub-decision, not pre-answered by CONTEXT.md or UI-SPEC, which only say "exact order the backend returns, no client re-sort") whether the new endpoint returns insertion order as-is (first-applied-first, stable across idempotent re-submits) or reverses to newest-first (matching `ScenarioTable`'s newest-first precedent elsewhere in the app). Either is defensible; document the choice in the plan.
**Warning signs:** A UAT scenario that re-submits the same constraint text twice and observes the overrides list item unexpectedly staying in its original position instead of moving to the top/bottom.

### Pitfall 4: Unconditional textarea clear on mutation success
**What goes wrong:** Following `CreateScenarioDialog`'s literal pattern (`onSuccess: () => resetForm()`) verbatim would clear the textarea whenever the HTTP call succeeds (200), including rejected-only, clarification-needed, and no-constraint-found responses — directly violating CONS-04 ("rephrase without losing their place") and UI-SPEC's explicit Input-preservation rule.
**Why it happens:** `POST /constraints` always returns `200` for these outcomes (they are not HTTP errors); "mutation succeeded" and "should clear the input" are two different conditions here, unlike `CreateScenarioDialog` where they're the same.
**How to avoid:** Gate the clear on the response body: `applied.length > 0 && clarification_needed === null`, evaluated inside the component's `.mutate(text, { onSuccess: (data) => { if (...) setText("") } })` callback — not inside `useApplyConstraint`'s own `onSuccess` (which only handles the invalidation, a response-shape-independent concern).
**Warning signs:** A UAT scenario where a rejected-only submission empties the textarea instead of preserving the user's text for editing.

### Pitfall 5: `run_service.py` / `insight_service.py` breaking on the added `parsed_constraint` key
**What goes wrong:** If the added key were consumed via `**v` unpacking or `dict(v) == {"tool": ..., "args": ...}` equality anywhere downstream, an added key would break it.
**Why it happens:** N/A here — **verified safe** by direct code read, not assumed. `run_service.py:90`: `OverrideCall(id=k, tool=v["tool"], args=v["args"])` — explicit key access, extra key ignored. `insight_service.py:161`: `{"tool": v["tool"], "args": v["args"]}` — same. Neither does equality comparison or full-dict unpacking against the stored value.
**How to avoid:** Keep the D-02 change strictly additive (add `parsed_constraint` key; do not rename/restructure `tool`/`args`). Confirmed safe with the current code; would need re-verification only if either reader is refactored in a later phase.
**Warning signs:** N/A this phase — documented here to save the planner from re-deriving this from scratch, per CONTEXT.md's "must tolerate... but verify" instruction.

### Pitfall 6: Treating "backfill legacy overrides" as free
**What goes wrong:** Backfilling `parsed_constraint` onto existing stored overrides (rather than the simpler graceful-fallback-at-read-time approach) requires, for each scenario with legacy overrides, reloading that scenario's fixture (`load_problem(os.path.join(data_dir, scenario["fixture"]))`) and re-running the same per-tool string-template logic currently *inline* inside `parse_and_store`'s per-tool branches (not extracted into a reusable function) — because the stored `args` already contain resolved GUIDs, a backfill needs `problem.task(...)`/member lookups to turn those back into display names, exactly duplicating logic that today only exists inline at parse-time.
**Why it happens:** It looks like a small data migration but actually requires either (a) extracting the six per-tool `parsed_constraint = f"..."` templates into a standalone function callable from both `parse_and_store` and a migration script, or (b) duplicating them in a one-off script — both are real engineering effort CONTEXT.md's migration note doesn't fully price in.
**How to avoid:** Default to the graceful-fallback approach UI-SPEC already specifies ("Legacy override fallback" copywriting row, `{Tool Label}: {comma-separated key=value args}` + "(legacy entry)" caption) and skip backfill unless the planner has a specific reason to invest in it (e.g. a real user-facing DB with meaningful legacy data — unlikely this early in a v0.4 milestone with local dev DBs).
**Warning signs:** A plan task titled "backfill parsed_constraint" that doesn't also include "extract per-tool template functions from `constraint_service.py`" as a prerequisite.

## Open Questions

1. **Overrides list ordering (first-applied vs newest-first)**
   - What we know: UI-SPEC only mandates "exact order the backend returns, no client re-sort." The stored dict's natural iteration order is insertion order (first-applied-first, stable across idempotent re-submits — Pitfall 3).
   - What's unclear: Whether "newest first" (matching `ScenarioTable`'s scenario-list convention elsewhere in the app) is the more consistent UX choice, or whether insertion order is fine since overrides don't have a visible timestamp in `AppliedConstraint`/`OverrideOut` to sort by anyway.
   - Recommendation: Default to backend-returns-insertion-order (simplest, zero extra code); note the choice explicitly in the plan so it's a documented decision, not an accident.

2. **Should the constraint-apply mutation also invalidate the scenario-detail query?**
   - What we know: `ScenarioOut` fields (`name`, `fixture`, `time_limit_s`, `created_at`) never change as a result of `POST /constraints`.
   - What's unclear: None functionally — this is a confirmed "no" — flagged only so the planner doesn't reflexively invalidate both query keys out of caution.
   - Recommendation: Invalidate only the overrides query key.
