# Phase 2: Scenario Detail + Plain-English Constraints - Context

**Gathered:** 2026-07-17
**Status:** Ready for planning

<domain>
## Phase Boundary

The Editor tab (mounted at the ScenarioLayout **index** route
`/scenarios/:scenarioId`, established in Phase 1) where a user opens a scenario,
sees every override currently applied to it, and shapes its constraints by typing
plain English — a readable parse echo, partial-apply (`applied[]` + `rejected[]`
in one `200`), a clarification-and-rephrase path, and a provider-down (`503`)
state distinct from "your constraint was invalid".

Delivers: SCEN-03 (scenario detail + applied-overrides list), CONS-01..05
(submit NL constraint, readable echo, partial-apply rendering, clarification,
provider-down handling). Plus the **one backend change** this phase requires:
a read path exposing a scenario's persisted overrides over HTTP (see D-01).

Requirements: SCEN-03, CONS-01, CONS-02, CONS-03, CONS-04, CONS-05.

**Not this phase:** `POST /constraints` does **not** trigger a solve — this phase
ends with overrides persisted and legible; seeing their *effect* is Phase 3
(run trigger + polling). Results/charts/insights are Phase 4. No override
deletion/editing (see Deferred).

</domain>

<decisions>
## Implementation Decisions

Four gray areas were surfaced and decided by the user. The central one (D-01)
carries a scope consequence: it adds a second backend change to a milestone that
scoped BE-01/CORS as the *only* backend change. The user chose it knowingly
because criterion 1 ("see **every** override currently applied") cannot otherwise
be met — there is no HTTP path today that returns a scenario's stored overrides.

### Applied-overrides source (SCEN-03, criterion 1)
- **D-01:** **Add a backend read path** that exposes a scenario's persisted
  overrides over HTTP. Today `ScenarioOut` (`backend/api/schemas.py:15`) omits
  overrides entirely and the `overrides` JSON column is never read back over the
  API — so `POST /constraints`'s `applied[]` is the *only* place override data
  reaches the client, which cannot show pre-existing overrides on open/reload.
  The read path fixes that: the Editor loads the full override list on mount and
  it survives reload. Shape (endpoint vs adding an `overrides` field to
  `ScenarioOut`) is the planner's call — either satisfies the requirement; a new
  field on `ScenarioOut` is the smaller diff, a dedicated `GET
  /scenarios/{id}/overrides` keeps `ScenarioOut` lean. **`docs/API.md` and the
  generated `schema.d.ts` must be updated in lockstep** with whatever shape is
  chosen (this repo has a documented history of doc/code drift — see Phase 1
  context D, commit `93ca4e0`).

### Override display fidelity (CONS-02)
- **D-02:** **Persist `parsed_constraint` alongside `{tool, args}`** in the
  scenario's `overrides` column. Currently the column stores only `{tool, args}`
  (confirmed in `constraint_service.py` and `insight_service.py:161`) — the
  human-readable echo is generated by the parser, returned in the `POST
  /constraints` response, then discarded on persist. Persisting it means a
  reloaded override reads **identically** to a freshly-applied one; one render
  path, one appearance, always readable. Rejected alternatives: humanizing
  `{tool, args}` in TypeScript (duplicates parser phrasing → drift risk; client
  only has the task *id* `T123`, not the name "Pick"), and accepting two
  fidelities (same override visibly changes after reload; reloaded form is the
  "raw tool-call JSON" CONS-02 forbids).
  - **Migration note for the planner:** existing scenarios may already have
    overrides stored *without* `parsed_constraint` (the pre-D-02 shape). The read
    path must degrade gracefully for those legacy entries (e.g. fall back to a
    tool+args rendering, or backfill) rather than assuming the field is always
    present.

### Constraint box interaction model (CONS-01, CONS-04)
- **D-03:** **Running transcript.** Keep a session log of each submission and its
  parse outcome (chat-like), rendered **above** the durable applied-overrides
  list. This makes the clarification-and-rephrase flow (criterion 4, "rephrase
  without losing their place") natural — the question stays in the transcript and
  the user re-submits. The transcript is **session-only** (not persisted); the
  overrides list (D-01) is the durable record. The transcript shows *attempts and
  outcomes*; the overrides list shows *what is currently applied*.

### Outcome-state rendering (CONS-03, CONS-04, CONS-05)
- **D-04:** **Four fully distinct treatments**, because one `POST /constraints`
  `200` can carry several of these at once and criterion 5 explicitly requires
  the provider-down state be visibly distinct from "invalid constraint":
  1. **`applied[]`** — added to the overrides list (and echoed in the transcript).
  2. **`rejected[]`** — per-item **inline** reason + valid options (the backend's
     `error` string already carries plain-English guidance, e.g. "factor must be
     positive, got -1. Use a value > 0…").
  3. **`clarification_needed`** (a `200` field, string|null) — shown as a question
     that invites a rephrase; user's text is not lost.
  4. **`503` provider-down** — a distinct banner ("the provider is unavailable"),
     **not** styled like a validation error.
  - **D-05:** Also handle the fifth outcome: **`no_constraint_found: true`** — a
    neutral "no constraint was recognized in that text" message (not an error, not
    a success). This is a real response field, not an edge case to ignore.

### Claude's Discretion (planner decides; not pre-answered)
- Exact backend shape for D-01 (field-on-`ScenarioOut` vs dedicated endpoint).
- Backfill vs graceful-fallback strategy for legacy overrides missing
  `parsed_constraint` (D-02 migration note).
- Visual layout of the transcript-above-overrides Editor (D-03) within the
  existing shadcn/ui + Tailwind system.
- Whether the overrides read uses its own TanStack Query key or extends the
  existing scenario-detail query; invalidation on successful apply.

</decisions>

## Existing Code Insights

### Reusable Assets (frontend, established in Phase 1)
- **`frontend/src/api/client.ts` + `schema.d.ts`** — single typed `openapi-fetch`
  client over the generated `paths` type. New endpoint calls (`POST /constraints`,
  the D-01 overrides read) go through this client; **regenerate `schema.d.ts`**
  after the backend change rather than hand-authoring payload types.
- **`frontend/src/api/scenarios.ts`** — thin typed endpoint wrappers deriving
  request/response types via indexed access into `paths` (not hand-written). The
  new constraint + overrides wrappers follow this exact pattern; the `error`
  path attaches `response.status` so callers can branch (the mechanism CONS-05's
  `503`-vs-`422` distinction needs).
- **`frontend/src/hooks/useScenarios.ts`** — TanStack Query wrapper pattern; the
  `["scenarios"]` query-key + mutation-invalidation contract is the template for
  the overrides read + apply-mutation-invalidates-overrides flow.
- **`frontend/src/components/ui/*`** — shadcn/ui primitives already present
  (`alert`, `button`, `input`, `table`, `dialog`, `select`, `tabs`) — the
  provider-down banner, rejection alerts, and overrides table build from these.
- **`frontend/src/components/layout/ErrorBanner.tsx`** — existing readable-error
  surface; the `503` provider-down banner (D-04) can reuse/extend it.

### Established Patterns (do not re-litigate)
- **Server state = TanStack Query** (Phase 1 D). No raw `fetch`+`useState`.
- **Types generated, never hand-written** — `openapi-typescript` → `schema.d.ts`;
  derive via indexed access. This is why `docs/API.md` + schema regen must move
  in lockstep with D-01.
- **shadcn/ui + Tailwind v4**, desktop-first (Phase 1 D-06). react-router.
- **Backend config via `settings.py` env pattern**; `LLM_PROVIDER=stub` default
  keeps CI keyless — nothing this phase adds may require a live key.

### Integration Points
- **`frontend/src/routes/EditorPlaceholder.tsx`** — the placeholder this phase
  replaces; mounts at the ScenarioLayout **index** route `/scenarios/:scenarioId`
  (`ScenarioLayout.tsx` — Editor is the index, a URL *prefix* of Runs/Results;
  the `NavLink end` handling there is already correct).
- **Backend override persistence** — `constraint_service.py`'s read-modify-write

  `parsed_constraint` key (they read `tool`/`args` by name, so an extra key is
  safe — but verify).

<specifics>
## Specific Ideas

- The transcript (D-03) is a **session log of attempts + outcomes**; the overrides
  list (D-01/D-02) is the **durable record of what is currently applied**. Keep
  these two conceptually and visually separate — the transcript answers "what did
  I try and what happened", the list answers "what is in effect right now".
- Rejection messages should surface the backend's own `error` string verbatim —
  it already contains plain-English guidance and valid options (CONS-03), so the
  UI renders it rather than reinventing the wording.

</specifics>

  polling). `POST /constraints` deliberately does not solve.
