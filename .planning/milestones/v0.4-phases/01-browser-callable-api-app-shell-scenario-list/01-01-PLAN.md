<planner_decisions>
Two questions RESEARCH.md left open; both are decided here, not delegated to the executor.

**Decision — `CORS_ORIGINS` default value (RESEARCH.md Open Question 2): `http://localhost:5173,http://localhost:4173`.**
Both Vite ports ship in the default: `5173` is `npm run dev`, `4173` is `npm run preview`
(which serves the built `dist/`). Criterion 5 requires the app to build to static assets, and a
built bundle that cannot talk to the backend without hand-editing env is a hollow build — so
`preview` is included. Two loopback origins is still an explicit, minimal allow-list.

**Known trap, must be documented in `.env.example`, not discovered later:** `http://127.0.0.1:5173`
is a *different origin* from `http://localhost:5173` and is deliberately NOT in the default.
A developer who browses to the `127.0.0.1` form will get a blocked request that looks identical
to "backend is down" (RESEARCH.md Common Pitfalls #5 — `fetch` cannot tell them apart). The
`.env.example` comment must name this explicitly so the failure is self-diagnosing.

**Decision — no Vite dev proxy** (RESEARCH.md Alternatives Considered, confirming the research
recommendation): dev traffic crosses a real origin boundary and exercises real CORS. A proxy
would hide a misconfiguration until first deploy, which directly defeats criterion 1's
"no CORS error in the console".
</planner_decisions>

<assumption_delta_decision>
The `assumption-delta` detector fired on this phase (`kind: chosen`, term `configurable`, from
criterion 5: *"Allowed origins are configurable rather than hardcoded"*). A constant became a
parameter, so the checkpoint asks whether a configuration decision has become a modeling decision.

- **Primary noun:** the **origin allow-list** (a set of origins), NOT "the frontend origin" (a singular).
- **Decision: `promote`.** Model `cors_origins` as `tuple[str, ...]` from birth. Never introduce a
  singular `cors_origin: str` with a later "and also a second one" bolted alongside.
- **Rationale:** the plural is not speculative — v0.4 needs **two** origins on day one (`:5173` dev,
  `:4173` preview, per the decision above), and any future deployed origin is a third. A singular
  model would be wrong before the phase even ships. Promoting costs nothing: the parse is one
  comma-split, and `CORSMiddleware` takes a list natively.
- **Companion invariant test (accepted, wired in Task 2):** `test_cors_reflects_every_configured_origin`
  is parametrized over a **multi-origin** `CORS_ORIGINS` and asserts each entry reflects
  independently. This goes red the instant someone reintroduces a first-entry-only assumption.
</assumption_delta_decision>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser origin → FastAPI app | An arbitrary web origin can attempt a cross-origin request. `CORSMiddleware` is the only control deciding whose response the browser is permitted to read. |
| OS environment → app config | `CORS_ORIGINS` is operator-supplied input that directly widens or narrows that control. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-1-01 | Tampering / Information Disclosure | `backend/api/main.py` `add_middleware(CORSMiddleware, ...)` | high | mitigate | Explicit env-configured origin allow-list sourced solely from `Settings.cors_origins`; never a wildcard origin list; `allow_credentials` omitted so it stays at Starlette's default False. Gated by the `allow_credentials=True` and wildcard-origin greps in Task 2's acceptance criteria, and by `test_cors.py`'s disallowed-origin assertion. |
| T-1-04 | Information Disclosure / Elevation of Privilege | the allow-list's breadth vs the app's documented no-auth posture | medium | accept | D-02 means every scenario is globally visible to anyone who can reach the API — already an explicitly accepted, documented risk (PROJECT.md "v0.4 key context" #1, "handle later"). This phase's obligation is only to not *widen* that exposure: the allow-list stays at the two loopback dev origins, so no new network reachability is introduced. Accepting, not mitigating, because closing it means building auth, which is explicitly out of scope for v0.4. |

No package-manager installs occur in this plan (it is pure backend Python against already-installed
