  <behavior>
    - `useFixtures()` queries `listFixtures` under the key `['fixtures']` and exposes loading/error/success.
    - `useCreateScenario()` mutates via `createScenario` and, on success, invalidates the `['scenarios']` query key.
    - `useCreateScenario()` performs no optimistic update — the `['scenarios']` cache is unchanged until the server confirms and the refetch lands.
    - A failed mutation surfaces the error (carrying its `status`) to the caller rather than swallowing it.
  </behavior>

  <action>
    Create `frontend/src/hooks/useFixtures.ts` exporting `useFixtures` — a `useQuery` with key
    `['fixtures']` and `queryFn` set to `listFixtures`, following RESEARCH.md Pattern 3.

    Create `frontend/src/hooks/useCreateScenario.ts` exporting `useCreateScenario` — a `useMutation`
    with `mutationFn` set to `createScenario` and an `onSuccess` that calls
    `queryClient.invalidateQueries` on the `['scenarios']` key, obtaining the client via
    `useQueryClient`.

    **The `['scenarios']` key must match plan 01-06's `useScenarios` exactly.** Read that file; do not
    retype the string from memory. This is the single highest-value link in the plan and its failure
    mode is invisible: a mismatched key means the POST succeeds, the mutation reports success, no error
    is raised anywhere, and the new row simply never appears. That reads as a backend bug and is not
    one.

    **Do not add an optimistic update.** TanStack Query's `onMutate` makes it a two-line change and it
    would make the new row appear instantly — and it is prohibited on this plan. An optimistically
    inserted row is a row the user can see that the backend has never heard of; if the POST then fails,
    the UI has already lied, and the rollback is a row vanishing for reasons the user cannot connect to
    anything. The invalidate-on-success path is slower by exactly one round trip and is honest at every
    instant. This project's whole design ethic — the honest wait in Phase 3, the `null` metrics in
    Phase 4, the "not built yet" placeholders in 01-05 — is this same trade made consistently.

    Let the mutation's error propagate to the caller with its `status` intact. The dialog needs it to
    choose between the 400 and 422 inline messages, which UI-SPEC renders in two different places.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user-typed scenario `name` → `POST /scenarios` → persisted → re-served to every browser (D-02) | The full stored-input round trip. The client's validation is a UX affordance; the server's Pydantic model is the boundary. |
| `fixture` value → backend filesystem read | The backend resolves the fixture name to a file under `ROSTERAI_DATA_DIR`. A known path-traversal weakness exists here (WR-04), which this phase does not touch and must not widen. |
