<objective>
Build the typed API client (SHELL-02) by generating types from the backend's own
OpenAPI schema, rather than hand-writing them from `docs/API.md`.

Purpose: D-01 locked TypeScript specifically because "hand-typed response shapes
drift silently", and CONTEXT.md names this repo's documented instance of exactly
that drift — commit `93ca4e0` exists because `docs/API.md` had diverged from the
code. Generating from `app.openapi()` makes the drift structurally impossible
rather than merely discouraged.

Output: a codegen pipeline, a committed `schema.d.ts`, one client instance, and three
thin wrapper functions for the endpoints this phase's UI actually calls.
</objective>

<planner_decisions>
**Decision — commit the generated `schema.d.ts` (RESEARCH.md Open Question 1): YES.**

The researcher recommended it; this plan adopts it, for a reason specific to this phase rather than
general preference. Criterion 5 requires the app to "build to static assets with one command". If
`schema.d.ts` were generated at install time, that command would silently require a *running Python
backend* to produce a *frontend static bundle* — a build-time dependency on a service the build has
no other reason to touch. Committing the file keeps `npm install && npm run build` self-contained.

The accepted cost: the committed file can go stale if someone changes a backend route without
regenerating. Mitigation is a documented `npm run codegen` step, not a CI drift-check — a drift-check
is a reasonable Phase 2+ follow-up but is not required by any Phase 1 criterion, and building one now
would be scope the phase did not ask for.

**Corollary decision — `frontend/openapi.json` is a build artifact, gitignored.** It is a pure
intermediate between `app.openapi()` and `schema.d.ts`. Committing both it and its derivative means
two files that can disagree with each other, which is a smaller version of the problem this plan
exists to solve. `schema.d.ts` is the committed derivative; the intermediate is regenerated on demand.

**Decision — API coverage.** See `COVERAGE.md` in this phase directory (written at plan time, per the
api-coverage gate, which fired on this phase). Three endpoints are wrapped (`GET /fixtures`,
`GET /scenarios`, `POST /scenarios`); eight are OPT-OUT with recorded reasons. Note the asymmetry that
makes those opt-outs cheap: `schema.d.ts` types **all eleven** endpoints regardless, because codegen
runs over the whole schema — so each opt-out is an unwritten ~4-line call site, not a missing
integration. Do NOT hand-trim the generated schema to only this phase's endpoints; that would be work
that adds risk and removes value.
</planner_decisions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| backend HTTP response → client code | Response bodies are untrusted input to the browser. The generated types describe the *expected* shape; TypeScript erases at runtime and enforces nothing on the wire. |
| build-time config → shipped bundle | `API_BASE_URL` is inlined into the public bundle at build time. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-1-02 | Information Disclosure | `frontend/src/api/scenarios.ts` — thrown error objects | medium | mitigate | Wrappers throw an error carrying the HTTP status and the backend's structured `detail`. That object must never be rendered raw to the user; the rendering contract is enforced at the surface (plans 01-05 through 01-07) via UI-SPEC's fixed non-diagnostic copy for unexpected failures. The wrappers' obligation here is narrower and worth stating: they attach `status` so callers can *branch* without needing to *display* anything the backend said. Known `4xx` `detail` strings (400 unknown fixture, 422 validation) are structured, non-sensitive text and are safe to reflect inline per UI-SPEC. |
| T-1-06 | Tampering | generated `schema.d.ts` vs the running backend | low | accept | TypeScript types erase at runtime, so a backend that returns a shape contradicting the generated types is not caught by the client — the UI would render `undefined` rather than reject the payload. Accepting rather than mitigating: adding runtime response validation (e.g. a schema validator on every response) is real scope this phase did not ask for, and the exposure is bounded — the backend is first-party, the schema is mechanically derived from it, and the failure mode is a cosmetic render fault rather than a security event under D-02 (no auth, no privileged data). Revisit if a Phase 2+ endpoint ever carries a trust decision. |
| T-1-05 | Information Disclosure | `API_BASE_URL` inlined into the bundle | low | accept | The backend origin is public by nature — it is the address the browser must call. No secret transits this path (D-02: no auth, no keys client-side). Documented in plan 01-03's threat model as the general `VITE_*` inlining property. |
</threat_model>
