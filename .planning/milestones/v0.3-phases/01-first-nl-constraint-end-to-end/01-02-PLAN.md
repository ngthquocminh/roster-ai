<objective>
Deliver the parse/store half of the seam: a user POSTs one plain-English sentence and a
scenario id, the stub provider turns it into a validated soft `OverrideCall`, and it is
persisted to the scenario's `overrides` JSON keyed by a stable content-hash id — with a
200 response echoing exactly what was understood. No solve is triggered here (D-06).

Purpose: This proves ROADMAP success criteria 1 and the injection/wire-format half of 4
(`StubLLMProvider` behind a `get_llm_provider` dependency, Claude-faithful `tool_use`
internally, provider-neutral `list[OverrideCall]` across the Protocol boundary). It is a
complete vertical slice through the API + persistence subsystem, independently testable.

Output: the vendor-agnostic `LLMProvider` Protocol + factory, the keyword-routed
`StubLLMProvider`, the `get_llm_provider` DI seam, the `POST /constraints` route + schemas,
the `constraint_service` (resolve-validate-merge-persist), and `ScenarioRepo.update_overrides`.

User story (phase goal): **As a** workforce scheduler, **I want to** state a staffing
floor in plain English, **so that** it is captured against my scenario without my editing
solver code or JSON. This plan delivers the capture + storage path.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client -> POST /constraints | Untrusted free-text + scenario_id enter the API. |
| constraint_service -> SQLite | Validated override JSON is written to the scenarios.overrides column. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-I1 | Tampering (SQL injection) | `ScenarioRepo.get`/`update_overrides`, scenario lookup | high | mitigate | All SQL uses parameterized placeholders (`?`/named params); scenario_id and JSON are never string-interpolated into SQL. Override args are stored as a serialized JSON value, not as SQL. |
| T-01-I2 | Information Disclosure (IDOR) | scenario_id in request body, no auth | medium | accept | The entire Phase-1 API is unauthenticated by design (local, single-user milestone; auth is out of scope per REQUIREMENTS "Out of Scope"). No ownership model exists to enforce. Residual risk documented; revisit if the API is exposed. |
| T-01-I3 | Tampering (hallucinated id) | `constraint_service` task resolution | high | mitigate | Every task reference is resolved+validated against the loaded `Schedulingproblem`'s real task ids/names before persistence; zero/ambiguous matches are rejected with a 400 — no unvalidated/hallucinated id is ever stored or reaches the engine (supports D-03 safety). |
| T-01-I4 | Denial of Service | free-text `text` field | low | mitigate | `ConstraintParseRequest.text` capped via `Field(max_length=2000)`; the stub does bounded regex work, no unbounded loops. |
| T-01-I5 | Tampering (lost update / WAL) | overrides JSON read-modify-write | medium | mitigate | Read-modify-write happens within one request connection then commits; content-hash keys make repeated writes idempotent. Concurrent writes to the same scenario could lose-update; acceptable for the single-user local model, residual accepted. |
| T-01-I6 | Denial of Service (solver) | stored override -> later solve | high | mitigate | Only a validated `set_min_workers_per_task` with `n > 0` and a real task id is stored; the engine applies it as a bounded soft round-2 penalty (plan 01-01), so a malformed/abusive constraint can never make a future solve infeasible. |
| T-01-SC | Tampering | dependency installs | low | accept | No new package installs (stub is stdlib `re`/`json`/`hashlib` + existing FastAPI/Pydantic); no `[ASSUMED]`/`[SUS]` packages. Real Claude SDK deferred to Phase 4. |
</threat_model>
