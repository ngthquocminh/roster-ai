<objective>
Deliver the on-demand insight endpoint as a single end-to-end vertical slice: a
`GET /runs/{run_id}/insights` that, on first call for a COMPLETED run, generates a
metric-grounded natural-language report off the event loop, runs the D-06 grounding
guard, caches it in `runs.insight_json`, and returns it; on a not-COMPLETED run it
returns a friendly 200 not-ready body (D-07); on a second call it returns the cache
without re-calling the provider (INS-04).

Purpose: This is the walking slice for Phase 3 — it makes the core user capability
real (fetch a plain-language explanation of a completed run) while establishing the
provider seam (`generate_insights`), the cache column, and the grounding guard that
the failure/honesty tests in plan 03-02 then exercise.

Output: `runs.insight_json` column + migration guard, `RunRepo.set_insight`,
`LLMProvider.generate_insights` + deterministic stub, `InsightOut` schema,
`services/insight_service.py` (orchestration + D-06 guard), the new route, and the
happy-path/not-ready/cache test file.
</objective>

## Phase Goal

**As a** scheduling operations user, **I want to** fetch a plain-language insight report for a completed run that cites the run's real metric values, **so that** I can understand what the schedule achieved without reading raw metrics JSON and without risking the computed schedule.

> Note: the ROADMAP `**Goal:**` line for Phase 3 is in prose form; the user story above is a faithful restatement (all three slots are present in the ROADMAP goal). No new scope is introduced.
