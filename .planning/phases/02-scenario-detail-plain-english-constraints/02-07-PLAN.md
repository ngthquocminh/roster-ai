<task type="checkpoint:human-verify" gate="blocking">
  <name>Task 1: Visual verification of the Editor outcome treatments, layout, and reload durability</name>
  <action>Run the running-app verification steps in <how-to-verify> below against the default keyless stub provider; confirm each of the five outcome treatments is visibly distinct (especially the 503 provider-down banner vs the red rejection), the header→transcript→input→overrides order, reload durability of overrides vs the session-only transcript, input-preservation, and the five long-text/422 backstops. This is a verification-only task — it changes no source files. Report "approved" or a punch-list of failing steps.</action>
  <what-built>
    The live Editor at /scenarios/:scenarioId: scenario detail header (with a 404 terminal view), a session constraint transcript, a plain-English constraint input, and a durable Applied Overrides list — backed by the new GET /scenarios/{id}/overrides endpoint and parsed_constraint persistence. All outcome states (applied / rejected / clarification / no-constraint-found / 503 provider-down) are implemented and unit-tested; this step confirms them visually against the default keyless stub provider.
  </what-built>
  <how-to-verify>
    1. Start the backend with the default stub provider (keyless, deterministic): from `backend/`, `uv run uvicorn api.main:app --reload` (LLM_PROVIDER defaults to stub).
    2. Start the frontend: from `frontend/`, `npm run dev`, then open the printed localhost URL.
    3. From Home, open a scenario (or create one). Confirm the Editor shows, top to bottom: the scenario header (name, fixture, time limit, created-at) → the constraint transcript region → the "Apply Constraint" input → the "Applied Overrides" list. Confirm the order is header → transcript → input → overrides.
    4. Apply a valid constraint (e.g. "keep at least 2 workers on Pick at all times"). Confirm: a transcript entry shows the readable parsed_constraint (Check icon, neutral) and a new row appears in the Applied Overrides list — as a readable sentence, NOT raw {tool,args} JSON. Confirm the textarea cleared.
    5. Apply a constraint that rejects (e.g. one producing "factor must be positive, got -1…" via a negative scale factor). Confirm the transcript shows "Couldn't apply: {label}" + the backend's error/options verbatim in red (destructive), and the textarea text is PRESERVED.
    6. Apply an ambiguous/unparseable text to trigger clarification, and a nonsense text to trigger no-constraint-found. Confirm each renders as a NEUTRAL message (not red, not success-green), with a rephrase caption, and the textarea text is PRESERVED in both.
    7. Confirm the 503 provider-down banner is visibly distinct from the red rejection styling. If reproducing a real 503 locally, temporarily set LLM_PROVIDER to a provider with no valid key (the backend maps provider errors to a clean 503), submit once, observe the neutral "The constraint parser is unavailable right now." banner, then revert to stub. (The 503→banner/not-destructive guarantee is also covered by the plan-02-05 automated test.)
    8. Reload the page. Confirm the Applied Overrides list still shows the same overrides (durable), and the transcript is empty again (session-only). Confirm the reloaded override reads identically to when it was freshly applied.
    9. Backstops: paste a very long scenario name / a near-2000-char constraint / observe a long rejection error, and confirm the header, overrides row, and transcript entries wrap or truncate without breaking layout. Confirm the character counter appears past 1,800 and the Apply button disables past 2,000.
    10. Visit a bad deep link (/scenarios/nonexistent-id) and confirm the terminal "Scenario not found" view with a "Back to Scenarios" button — and that no transcript/input/overrides render beneath it.
  </how-to-verify>
  <resume-signal>Type "approved" if all checks pass, or list the specific steps that failed (they become a gap-closure plan).</resume-signal>
