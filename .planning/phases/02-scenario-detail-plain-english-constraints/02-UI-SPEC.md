**Accent color reality check (important — read before touching color).** Phase 1's UI-SPEC *declared* `#4F46E5` (indigo-600) reserved for "the New Scenario primary button, the active-tab indicator, and the focus ring" — but the shipped code only actually applies it to the active-tab indicator (`ScenarioLayout.tsx`, arbitrary-value classes `border-[#4F46E5] text-[#4F46E5]`). The "New Scenario" button uses shadcn's stock `Button` `default` variant, which resolves to `bg-primary` — a **grayscale** near-black (`oklch(0.205 0 0)`, `--primary` in `index.css`), not indigo. The focus ring (`focus-visible:ring-ring/50`) is likewise grayscale, not indigo. This is a real, verified gap between Phase 1's spec and Phase 1's shipped pixels — not something to silently repeat, but also not this phase's to retroactively fix (out of scope; Phase 1 is closed). **Decision for Phase 2:** match what is actually live in the browser today, not what Phase 1's prose claimed. New buttons in this phase (`Apply Constraint`) use the same stock `Button` `default` variant (grayscale `bg-primary`) as "New Scenario" already does — so the two primary CTAs look identical, which is the correct visual-consistency outcome. `#4F46E5` stays reserved *exclusively* for nav/active-indicator-style elements, matching its one real, verified surface. See Color section below.

## Application Structure

Replaces `frontend/src/routes/EditorPlaceholder.tsx` at the ScenarioLayout **index** route `/scenarios/:scenarioId` (established in Phase 1; the tab-nav chrome around it is unchanged).

**Vertical layout, top to bottom, in this fixed order:**

1. **Scenario detail header** (SCEN-03) — scenario name (Heading role, 20px/600 — see Typography note below on why not Display), with fixture (monospace, matching `ScenarioTable`'s fixture-column convention), `time_limit_s`, and `created_at` as Label-role (12px, muted-foreground) captions beside/below it.
2. **Constraint transcript** (D-03) — the session log of submission attempts + outcomes. Renders **nothing** (not even empty-state chrome) until the first submission this session (see UI Considerations E3/empty). When populated: newest entry at the bottom, chat convention, auto-scrolls into view on a new entry, scrolls internally past a fixed height.
3. **Constraint input box** (CONS-01) — a `Textarea` + "Apply Constraint" submit button, sitting directly below the transcript as its compose row. Placeholder: `"e.g. keep at least 2 workers on Pick at all times"`.
4. **Applied Overrides list** (SCEN-03/D-01/D-02) — the durable record of what is currently applied. Heading-role (20px/600) section title "Applied Overrides" above it — deliberately heavier-weight than the transcript's caption (below), so the durable list visually outweighs the ephemeral log, matching D-03's "list is the record, transcript is the attempts" split.

**Why this order:** D-03 requires the transcript to render *above* the durable overrides list. Placing the input box between the two (rather than above the transcript, or below the overrides list) keeps the compose row anchored directly beneath the conversation it extends — the standard chat-UI convention — while still satisfying the literal "transcript above overrides" ordering.

**Why the scenario name is Heading (20px), not Display (28px):** Display is reserved, per Phase 1's typography note, for "the page title, used once per view" (Home's "Scenarios"). The Editor is not a top-level page — it is nested one level under the global app bar *and* the scenario-scoped tab nav, both already established chrome. A second 28px element here would compete with that chrome rather than sit inside it. Heading (20px) matches the precedent already set by the "New Scenario" modal title.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | "Apply Constraint" (submit button below the transcript; disabled while the textarea is empty, over 2000 chars, or a submission is already in flight) |
| Submit CTA — in flight | Spinner + "Applying…" (button disabled; textarea also disables for the duration — mirrors `CreateScenarioDialog`'s whole-form-disables-on-submit pattern, preventing a second submit before the first resolves) |
| Textarea placeholder | "e.g. keep at least 2 workers on Pick at all times" |
| Character-limit helper | Appears once the textarea passes 1,800 characters: "{n}/2000" (Label role, 12px); submit disables past 2,000 — this is a client-side backstop against a guaranteed `422`, not a copy the user needs to read normally |
| Applied outcome (transcript, per item) | The persisted `parsed_constraint` string, rendered verbatim, prefixed with a `Check` icon (neutral/foreground, not accent) |
| Rejected outcome (transcript, per item) | "Couldn't apply: {Tool Label}" (see Tool Label Map below) as a heading line, with the backend's `error` string rendered verbatim beneath it — both in `text-destructive`, prefixed with an `X` icon |
| Clarification outcome (transcript) | "Needs clarification: {clarification_needed text, verbatim}" — neutral/muted treatment (not destructive, not accent), with a caption below: "Rephrase your constraint above and submit again." The textarea's typed text is **preserved**, not cleared, so the user can edit in place (CONS-04's "without losing their place") |
| No-constraint-found outcome (transcript) | "No constraint was recognized in that text." — neutral/muted, no icon. Caption: "Try rephrasing — for example: \"keep at least 2 workers on Pick at all times.\"" |
| Provider-down banner (`503`) | Heading: "The constraint parser is unavailable right now." Body: "The LLM provider couldn't be reached. Your constraint wasn't lost — edit it if needed and try again in a moment." Rendered as a distinct `Alert` (`default` variant — **not** the `destructive` variant, and visually distinct from the SHELL-04 backend-unreachable banner's copy) so it never reads as "your input was wrong" (D-04/CONS-05) |
| Applied-overrides empty state | Heading: "No constraints applied yet" Body: "Type a plain-English constraint below to add one." (mirrors Phase 1's "No scenarios yet" phrasing for consistency) |
| Applied-overrides loading | "Loading overrides…" (centered, spinner — mirrors `ScenarioTable`'s loading treatment) |
| Applied-overrides error (fetch failure) | Reuses the existing `ErrorBanner` component/copy (SHELL-04 pattern) — not a new error surface |
| Legacy override fallback (D-02 migration — `parsed_constraint` missing) | "{Tool Label}: {comma-separated `key=value` args}" in italic, muted-foreground, with a trailing caption "(legacy entry)" — honest about lower fidelity rather than inventing a fabricated humanized sentence the client cannot safely construct (it lacks task/member name lookups) |
| Scenario-not-found (`404` on `GET /scenarios/{id}`) | Heading: "Scenario not found" Body: "It may have been removed, or the link is incorrect." + a "Back to Scenarios" button routing to `/` — resolves Phase 1's `E5` backstop (bad `:scenarioId` deep link) |
| Destructive confirmation | Not applicable — no destructive action exists in Phase 2 (overrides are not deletable; see Deferred in `02-CONTEXT.md`) |

**Tool Label Map** (used for rejected-item headings and legacy-fallback rendering — a fixed lookup, not a runtime humanization attempt):

| `tool` value | Label |
|---|---|
| `lock_worker_shift` | "Lock worker shift" |
| `set_min_workers_per_task` | "Minimum workers per task" |
| `exclude_worker_from_task` | "Exclude worker from task" |
| `scale_demand` | "Scale demand" |
| `set_max_hours` | "Max hours" |

**Input-preservation rule (generalizes CONS-04 across all non-success outcomes):** the textarea clears **only** when the response contains at least one `applied[]` item **and** `clarification_needed` is `null`. In every other case — rejected-only, `clarification_needed` present, `no_constraint_found: true`, or a `503` — the typed text is preserved so the user can edit and resubmit without retyping.

**Planner note — the five backstops.** Each lifts into `must_haves` as `{ statement, verification: backstop }`, not as a plain truth. At verify time a backstop with no wired evidence routes to `insufficient_spec → human_needed` rather than passing silently. Two (E1, E2 long-text) are visual truncation/wrapping checks that genuinely cannot be asserted at spec time. One (E3 long-text) is the same class for the transcript. One (E4 `422`) and one (E5 long-text) are structural-backstop cases: the code path must exist and be correct, but this UI's own client-side gating makes it visually unreachable in the ordinary flow — the same shape as `CreateScenarioDialog`'s pre-existing `422` handling, which is a real precedent for "the server branch stays, even when the client rarely triggers it."

**Note on the D-01 backend read path (not this file's call).** `02-CONTEXT.md` leaves the exact shape of the overrides read (a new field on `ScenarioOut` vs. a dedicated `GET /scenarios/{id}/overrides` endpoint) to the planner. This contract is written against the *rendered result* — a list of `{ parsed_constraint }`-shaped entries (or the legacy fallback) — and is agnostic to which HTTP shape produces it. Whichever shape the planner picks, `docs/API.md` and `schema.d.ts` must move in lockstep (per `02-CONTEXT.md` D-01).
