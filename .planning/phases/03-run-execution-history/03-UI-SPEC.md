**Inherited, not re-litigated.** This phase adds **zero** new design-system decisions and **zero new shadcn components** — `Button`, `Alert`, and `Table` (all already installed from Phases 1-2) are sufficient. No `Badge` is introduced for run status: Phase 2 established an icon+text convention for outcome states (`Check`/`X` from `lucide-react`, neutral or destructive text — see `TranscriptEntry.tsx`) rather than a pill/badge idiom, and this phase's four run states (`PENDING`/`RUNNING`/`COMPLETED`/`FAILED`) map cleanly onto that same convention. Introducing `Badge` here would create a second status idiom running in parallel with the first, which Phase 2's Design System note explicitly avoided doing for containers (`Card` vs. plain bordered `div`s) — same reasoning extended to status display.

**Accent color:** no new accent surface this phase. The "Run Scenario" button uses the stock `Button` `default` variant (grayscale `bg-primary`), matching "New Scenario" and "Apply Constraint" — consistent with Phase 2's verified finding that `#4F46E5` (indigo-600) is live on exactly one surface (the active-tab nav indicator) and every primary-CTA button in this app is actually grayscale, not indigo. This phase does not disturb that reality.

Registry safety gate: not applicable this phase (shadcn official registry only, no new blocks — see Registry Safety).

## Application Structure

Replaces `frontend/src/routes/RunsPlaceholder.tsx` at the ScenarioLayout route `/scenarios/:scenarioId/runs` (the "Runs" tab established in Phase 1; the tab-nav chrome around it is unchanged — this phase does not modify `ScenarioLayout.tsx`'s nav).

**Vertical layout, top to bottom:**

1. **View header row** — "Run History" as this view's title (Heading role, 20px/600 — not Display/28px, for the same reason Phase 2's scenario name used Heading: this view is nested under the global app bar *and* the scenario-scoped tab nav, both already established chrome; a second 28px element would compete with it) with the **"Run Scenario" primary CTA** (RUN-01) anchored top-right — mirrors Home's "New Scenario" header-button placement precedent exactly.
2. **In-flight status panel** (RUN-03, conditional) — an `Alert` (`default` variant, same non-toast persistent-inline philosophy as `ErrorBanner`/`ProviderDownBanner`) rendered **only** while the run list contains at least one non-terminal run (`PENDING` or `RUNNING`). Shows the newest such run's honest-wait copy (see Copywriting Contract). Renders nothing — not even empty chrome — when no non-terminal run exists.
3. **Run history table** (RUN-04) — every run for this scenario, newest-first (server ordering, no client re-sort — same principle as `ScenarioTable`). Columns: Status | Created | Started | Finished. A `FAILED` row's `error` text renders inline beneath its status label (RUN-05), not hidden behind a click.

**Data strategy (load-bearing for RUN-02/RUN-03, not just cosmetic):** a single polling query against `GET /scenarios/{id}/runs` — the list endpoint, not per-run polling of `GET /runs/{id}` — drives both the in-flight panel and the table from one response. Poll while the fetched list contains any `PENDING`/`RUNNING` run; stop polling once every run in the list is terminal. On a successful `POST /scenarios/{id}/runs`, refetch/invalidate this same query immediately so the new `PENDING` run appears **without waiting for the next poll tick** — this is what makes RUN-01's "appear immediately" literally true rather than eventually-true.

**"Run Scenario" button behavior:**
- Disabled while the list query is still loading (avoids a flash of an enabled button before the true in-progress state is known) **and** while the fetched list already contains a `PENDING` or `RUNNING` run (single-worker-pool honesty — the UI doesn't let a user queue up runs the backend can only serialize one at a time anyway; RUN-03's "genuinely slow" note is exactly why this matters). A disabled-state caption explains why (Copywriting Contract).
- On click: `POST /scenarios/{scenario_id}/runs`. Success → the response's `PENDING` `RunOut` is what appears at the top of the list (via the immediate refetch above). Failure → inline error beneath the button, branching on status per the established `getErrorStatus`/T-1-02 convention (404 vs. other) — see Copywriting Contract. The button re-enables; nothing is lost since triggering a run has no user-typed state to preserve.

**Row navigation:** every row (any status) is clickable — same `tabIndex`/`onClick`/`onKeyDown` (Enter/Space) pattern as `ScenarioTable`'s rows — and navigates to `/scenarios/:scenarioId/runs/:runId`. This is deliberately the resolution of `ScenarioLayout.tsx`'s existing comment ("the in-app link source is deferred to Phase 3 — first run produced"): the run-history row is that link source. **Explicitly out of scope:** enabling the ScenarioLayout "Results" **tab** itself (it stays disabled) — that tab activating to point at a specific run is Phase 4's concern once `ResultsView` is real content worth landing on directly from tab nav, not Phase 3's.

**`solver_status` is deliberately never rendered in this view.** RUN-04 asks for run `status` (`PENDING`/`RUNNING`/`COMPLETED`/`FAILED`) and timing only — not `solver_status`. This sidesteps the "`COMPLETED` + `solver_status: UNKNOWN` is success, not failure" hazard entirely rather than needing an in-place caveat: a `COMPLETED` row always reads as unambiguous, neutral success here, regardless of what the solver actually achieved. `solver_status` and coverage detail belong to Results (Phase 4 / RES-01).

**Verified backend edge (see UI Considerations E4):** `GET /scenarios/{scenario_id}/runs` does **not** 404 for an unknown `scenario_id` (`runs.py:38-40` — `list_runs` calls the repo directly with no existence check), unlike `POST /scenarios/{scenario_id}/runs` which does. A direct deep link to a bogus scenario's Runs tab therefore renders the ordinary empty state, not a "Scenario not found" gate.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | "Run Scenario" (top-right of the Run History view; triggers `POST /scenarios/{id}/runs`) |

| Loading state | "Loading runs…" (centered spinner, mirrors `ScenarioTable`/`OverridesList`) |
| Error state (list fetch fails) | Reuses the existing `ErrorBanner` component/copy (SHELL-04 pattern) — not a new error surface |
| Destructive confirmation | Not applicable — no destructive action exists in this phase (no run cancellation, no run deletion; RUN-03 explicitly forbids a cancel affordance) |
