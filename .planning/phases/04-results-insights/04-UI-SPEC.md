## Application Structure

Replaces `frontend/src/routes/ResultsPlaceholder.tsx` at the ScenarioLayout route `/scenarios/:scenarioId/runs/:runId` (the "Results" tab established in Phase 1, disabled until a run exists; Phase 3 made the tab highlight correctly via `useMatch` but left it non-clickable — this phase does not modify `ScenarioLayout.tsx`'s nav chrome, and does not enable the Results tab as a static link, per Phase 3's explicit scope boundary).

**Branch on `RunOut.status` first (D-12) — before anything else renders:**

```
useRun(runId)  →  GET /runs/{run_id}   (RunOut, always succeeds regardless of status)
   ├─ PENDING / RUNNING  → render <RunInFlightPanel run={run} /> verbatim (reused from Phase 3,
   │                        zero new copy). Nothing else on the page renders below it — no
   │                        coverage/chart/schedule/insight section, since /result would 409.
   ├─ FAILED             → render a page-level destructive Alert: title "Run Failed", body
   │                        run.error, falling back to RunHistoryTable's exact
   │                        FAILED_NO_ERROR_COPY string when error is null/empty (D-12: "no new
   │                        copy invented for states already solved in Phase 3" — this reuses
   │                        that fallback verbatim rather than writing a second one).
   │                        Nothing else on the page renders below it.
   └─ COMPLETED          → gate useRunResult(runId) on this status; render the full results
                            body (sections 1-5 below).
```

**Vertical layout, top to bottom, once `COMPLETED` and `RunResult` has resolved:**

1. **View header row** — "Run Results" (Heading role, 20px/600 — same reasoning as Phase 3's "Run History": this view is nested under both the global app bar and the scenario tab nav, so a 28px Display title would compete with already-established chrome). Directly beneath it, a muted-foreground metadata line reusing `formatTimestamp`: "Completed {finished_at}" (falls back to "—" only if literally absent, which should not happen for a `COMPLETED` run). No page-level primary CTA here — unlike Home's "New Scenario" or Runs' "Run Scenario", this view's one on-demand action (insight generation) is scoped to its own section (5), not a global page action.
2. **Warnings banner (D-06, RES-06)** — conditional; renders **only** when `warnings.length > 0`, directly above the stat row, so the coverage-honesty caveat is read before the numbers it qualifies. Renders nothing (not even empty chrome) when the array is empty. `warnings ?? []` guard at the one call site (RESEARCH.md Open Question 1 — defends against pre-`warnings`-era cached `result_json` rows).
3. **Coverage stat row (D-04, RES-01) + coverage-by-day breakdown table (D-05)** — two `Card`s side by side ("Total Cost", "Total Unmet Hours") above a breakdown table (Day | Coverage %). Null `total_cost`/`total_unmet_hours` render literal "Not computed" + `Tooltip` (D-07); null per-day values render literal "Not computed" text inline (same honesty principle, no tooltip needed at that granularity — see Copywriting Contract).
4. **Demand-vs-served chart (D-02, D-03, RES-02)** — one grouped-bar pair (`required_h` outline, `served_h` indigo fill) per function. **Never shows the same number the breakdown table shows** — chart is by-function only, table is by-day only (D-02/D-05's explicit no-duplication rule).
5. **Schedule table (D-08, D-09, D-10, RES-03)** — scrollable container reusing `RunHistoryTable.tsx`'s exact `max-h-[420px] overflow-y-auto rounded-md border border-border` pattern, server order only (no client sort/filter, D-09). Columns: Member | Task | Function | Shift Window — shift window via `formatShiftWindow` (Day N, HH:MM–HH:MM; Day N, HH:MM – Day N+1, HH:MM for shifts crossing midnight).
6. **Insight panel (D-11, D-13, RES-04, RES-05)** — its own bordered section at the bottom of the page. Idle state shows a heading, one line of body copy, and the "Get Insight Report" button (D-11: button-triggered, never auto-fetched on mount). This section's `useMutation`-backed fetch is structurally isolated from every section above it (Pattern 3, RESEARCH.md) — a `502` here re-renders only this section; sections 2-5 stay mounted and interactive (RES-05's hard requirement).

**Day-indexing consistency rule (binds sections 3 and 5 together — the single most important cross-component rule in this spec, per RESEARCH.md Pitfall 2).** Both the breakdown table (section 3) and the schedule table's shift-window column (section 5) use **1-indexed "Day N" labels** (Day 1 = hours 0–24, matching `docs/API.md`'s own worked example, "day-2 06:00 = 30.0h"). The breakdown table converts its raw 0-indexed `coverage_by_day` dict keys via `Day ${Number(dayKey) + 1}`; the schedule table's `formatShiftWindow` computes `Math.floor(totalMinutes / 1440) + 1`. These must never disagree on-screen for the same calendar day — if a component is built against the raw 0-indexed key without this conversion, that is a spec violation, not a style choice.

**Null-value guard rule (binds sections 3 and 4 — RESEARCH.md Pitfall 5).** `total_cost`, `total_unmet_hours`, every `coverage_by_day[N]`, and every `coverage_by_function[fn].required_h`/`served_h`/`pct` are independently nullable. Each is guarded **at the point it renders**, not once at the top of the response — a `null` never reaches `.toFixed()`, never silently becomes `0`, and never renders as a bare em dash (that convention is reserved for "field never applicable," e.g. Phase 3's missing timestamps — a null solver metric is a different, more load-bearing fact: "the solver didn't get to this," and must say so).

**Planner note — the three backstops.** Each lifts into `must_haves` as `{ statement, verification: backstop }`, not as a plain truth. The two long-text backstops (E2 warnings, E7 insight report) are genuine visual-wrap checks that cannot be asserted at spec time, matching Phase 3's `FAILED`-error long-text precedent exactly.
