  <behavior>
    - `useScenarios()` issues the query via `listScenarios` under the query key `['scenarios']`.
    - It exposes loading, error, and success states from TanStack Query rather than deriving them by hand.
    - It performs no transformation of the response — the data it returns is element-for-element what `listScenarios` returned, in the same order.
  </behavior>

  <action>
    Create `frontend/src/hooks/useScenarios.ts` exporting `useScenarios`, a `useQuery` with query key
    `['scenarios']` and `queryFn` set to `listScenarios` from `src/api/scenarios.ts`, following
    RESEARCH.md Pattern 3.

    **The query key string `'scenarios'` is a cross-plan contract.** Plan 01-07's create mutation
    invalidates this exact key to make a newly created scenario appear without a manual refetch. If the
    two keys differ by even a character, creation will succeed, no error will be raised anywhere, and
    the new row simply will not appear — a silent failure that looks like a backend bug.

    Do not sort, reverse, filter, or re-shape the response. The backend returns scenarios newest-first
    and owns that ordering (`docs/API.md`: "List all scenarios, newest first"). A client-side sort would
    be a second, competing source of truth for order that agrees with the server right up until it does
    not.

    Do not add `refetchInterval` here. Polling is Phase 3's need (run status), not this list's; a
    background poll on the scenario list would be invented behaviour with a real cost and no
    requirement behind it.
  </action>

  <action>
    Create `ScenarioTable.tsx` consuming `useScenarios()` and rendering the five states above on the
    shadcn `table` primitive. Mount it into `Home.tsx` beneath the existing "Scenarios" page title.

    **State-by-state, the UI-SPEC decisions that are easy to "improve" and must not be:**

    - *Loading:* a centered spinner plus `Loading scenarios…`. **No skeleton rows.** Skeletons are the
      fashionable choice and UI-SPEC rejects them deliberately: a skeleton flashes fake content before
      real data exists, which is precisely the pretence this project's surfaces avoid.
    - *Empty:* the empty state **replaces** the table — no header row over a void. The "New Scenario"
      button repeats inline here as the sole action. This is the one state where the button, not the
      table, is the focal point (UI-SPEC's Application Structure explains the inversion: with no table
      there is no content to be primary). The button is not yet wired to anything in this plan — plan
      01-07 attaches the dialog. Render it; leave it inert, and note that in the SUMMARY.
    - *Error:* render `ErrorBanner` and **no rows at all** — not stale rows from a previous successful
      fetch, and not partial data. A table showing yesterday's rows above a "can't reach the API"
      banner asks the user to decide which half to believe.
    - *Populated:* rows in response order — name, fixture filename in monospace, created timestamp.
      Row click navigates to `/scenarios/:scenarioId` (the Editor tab, a placeholder in this phase).
      That row-click IS the nav path criterion 3 depends on: it is how a user reaches the
      scenario-scoped routes without four flat global links that would be meaningless before a scenario
      is selected.
    - *Overflow:* the list scrolls inside a fixed-height container past roughly 10 rows. **No
      pagination** — this is portfolio-scale data, not a multi-tenant product, and pagination is a
      whole interaction surface v0.4 did not ask for.

    **No count label and no singular/plural copy anywhere** ("1 scenario" / "3 scenarios"). UI-SPEC
    E1/zero-one-many is explicit: one row renders identically to many. A count label is a second
    representation of the row count that can disagree with the rows themselves, and its singular/plural
    grammar is one more thing to get wrong for no gain.

    **Do not dedupe or merge same-named rows.** Scenario names are free text with no server-side
    uniqueness constraint (`docs/API.md`: `name` is `non-empty`, nothing more), so two scenarios can
    legitimately share a name. The `id` is the identity. Keying React list children by `name` would
    both warn and silently drop rows; key by `id`.

    **Do not sort.** The server returns newest-first and owns the ordering. Applying a client-side sort
    on `created_at` looks harmless and breaks the moment two rows share a timestamp — the tie-break
    would be the client's invention, contradicting the server's order for no reason.

    **Render the scenario `name` only as JSX text children.** React escapes text nodes by default, which
    is the complete mitigation for T-1-03 — no sanitization library is needed and none should be added.
    React's raw-HTML escape hatch must not appear anywhere under `frontend/src`: not in code, not in a
    comment, not in a "we deliberately don't use this" note. Its total absence is what makes the check
    meaningful.

    Create `ScenarioTable.test.tsx` covering every `<behavior>` case. Mock `useScenarios` (or the
    `../api/scenarios` module) with `vi.mock` — never `msw` (`[SLOP]`, plan 01-02). Render inside a
    memory router so the row-click navigation assertion has somewhere to go.

    For the ordering test, use two rows with **identical** `created_at` values; for the adjacency test,
    two rows with **identical** `name` values and different `id`s. Both fixtures are constructed so
    that a client-side sort or a name-keyed dedupe would fail the test rather than sail past it.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| scenario `name` (user-supplied, persisted, re-served) → rendered DOM | Under D-02 every scenario is globally visible, so one user's `name` renders in every user's browser. This is a genuine stored-XSS shape, even in a portfolio POC. |
| `GET /scenarios` response → rendered UI | Untrusted response body; TypeScript erases at runtime and enforces nothing on the wire. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-1-03 | Tampering | `ScenarioTable.tsx` — rendering of the user-supplied `name` | medium | mitigate | React's default JSX text-node escaping is the complete and sufficient control — the `name` is only ever rendered as JSX children. No sanitization library is added (it would be redundant and would imply the escaping is insufficient). The mitigation is enforced negatively: React's raw-HTML injection prop must not appear anywhere under `frontend/src`, gated by a repo-wide grep in this plan's acceptance criteria AND re-asserted in plan 01-07 (which adds the last code to `frontend/src` this phase — a gate that passes in Wave 4 cannot speak for what Wave 5 adds). Positively gated by a test rendering HTML-looking text in a `name`. |
| T-1-02 | Information Disclosure | error state of the list | medium | mitigate | A failed `GET /scenarios` renders `ErrorBanner` (plan 01-05), whose copy is a fixed literal and which never renders the caught error's message, stack, or the backend's raw `detail`. This plan's obligation is only to route the failure there rather than rendering the error itself. |
</threat_model>
