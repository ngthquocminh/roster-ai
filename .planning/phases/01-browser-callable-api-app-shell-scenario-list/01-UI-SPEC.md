# Phase 1 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Design System

| Property | Value |
|----------|-------|
| Tool | shadcn (init deferred to Phase 1 execution — see note) |
| Preset | Not a copy-pasted preset token. Pinned params instead: `--template vite --base radix --css-variables` (style: **new-york**, base color: **neutral**) |
| Component library | Radix primitives (via shadcn) |
| Icon library | lucide-react (shadcn default) |
| Font | System font stack (`ui-sans-serif, system-ui, sans-serif` — Tailwind's default `font-sans`). No web font load. |

**Why shadcn, decided here (this was this phase's one open discretion item):** `frontend/` is genuinely greenfield — nothing exists to inherit, and this choice propagates through Phases 2-4 (forms, tables, dialogs, status badges, and Phase 4's chart all sit inside whatever is chosen here). shadcn was picked over hand-rolled CSS Modules / plain CSS because:
- Components are generated into the repo as owned, readable TSX — not a hidden node_modules black box. That matches this project's demonstrated preference this session for decisions that cannot silently drift (the same session that retired stale `docs/` tracking).
- Tailwind utility classes are visible in the markup — no separate stylesheet to fall out of sync with the component, which is the same "honest surface" instinct the roadmap already applies to Phase 3's wait-copy and Phase 4's `null` metrics.
- The component set this milestone needs (forms, `Select`, `Dialog`, `Table`, `Tabs`, `Alert`, status badges) is exactly shadcn's core catalogue — no gaps to hand-build.
- It is copy-in code, auditable at a glance — appropriate for a portfolio project meant to demonstrate engineering, not just produce a UI.

**Why init is deferred, not run now:** `npx shadcn init` requires an existing `package.json`/Vite project to attach `components.json` to (verified against current CLI docs via context7 — `shadcn init -t vite -b radix -y --css-variables`, non-interactive). `frontend/` does not exist until Phase 1's plan/execute creates the Vite scaffold (SHELL-01). Running init is therefore a **mechanical first step of Phase 1 execution**, not a UI-SPEC action — this contract pins the parameters (template `vite`, base `radix`, style `new-york`, base color `neutral`, CSS variables on) so that step requires no design judgment when it happens. Note from context7 lookup: the CLI's non-interactive minimal-config path hardcodes base color to `neutral` — this pin matches that default rather than fighting it.

Registry safety gate: not applicable this phase (shadcn official registry only, no third-party blocks — see Registry Safety below).

## Application Structure

Not in the base template, added because SHELL-03/04 require a concrete route map and nav architecture that later phases build directly into — this is load-bearing for the planner and for Phases 2-4.

**Routes (React Router, all deep-linkable):**

| Route | View | Phase 1 state |
|---|---|---|
| `/` | Home (scenario list + create) | Fully built this phase |
| `/scenarios/:scenarioId` | ScenarioEditor | Reachable placeholder (Phase 2 builds it) |
| `/scenarios/:scenarioId/runs` | RunHistory | Reachable placeholder (Phase 3 builds it) |
| `/scenarios/:scenarioId/runs/:runId` | ResultsView | Reachable placeholder (Phase 4 builds it) |

**Nav has two tiers, and both are established now so later phases mount into existing slots rather than restructuring:**

1. **Global app bar** (persistent, all routes): "ShiftMind" wordmark, links to `/` (Home). No user menu, no auth affordance (D-02). This is the only *global* nav destination in Phase 1 — Editor/History/Results are scenario-scoped and have no meaning without a `:scenarioId`.
2. **Scenario-scoped tab nav** (persistent within `/scenarios/:scenarioId/*`): three tabs — "Editor" / "Runs" / "Results" — routing to the three scenario-scoped routes above. In Phase 1 all three render the placeholder (see Copywriting Contract); Phases 2-4 replace the placeholder body behind the same tab, not the tab itself.

Clicking a row in the Home scenario list navigates to `/scenarios/:scenarioId` (the Editor tab, placeholder in this phase). This is how criterion 3 ("move between routes through persistent nav, deep-link by URL") is satisfied end-to-end without inventing four flat global links that don't make sense before a scenario is selected.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label | 12px | 400 (regular) | 1.2 |
| Body | 14px | 400 (regular) | 1.5 |
| Heading | 20px | 600 (semibold) | 1.2 |
| Display | 28px | 600 (semibold) | 1.2 |

Two weights only: 400 (regular) and 600 (semibold) — no other weight is used anywhere in this phase.

14px body (rather than 16px) is a deliberate choice for a data-dense admin surface: the scenario table, and later the override list (Phase 2) and schedule table (Phase 4), all inherit this base. Display (28px) is used once per view — the page title ("Scenarios"). Heading (20px) is used for the modal title ("New Scenario") and any section headers.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#FAFAFA` (neutral-50) | Page background |
| Secondary (30%) | `#F5F5F5` (neutral-100) / `#E5E5E5` (neutral-200 for borders) | App bar, tab nav, table header row, card/dialog surfaces |
| Accent (10%) | `#4F46E5` (indigo-600) | Primary CTA button fill, active tab/nav indicator, focus ring, links |
| Destructive | `#DC2626` (red-600) | Destructive actions only |

Accent (`#4F46E5`) reserved for exactly: the "New Scenario" primary button, the active-tab underline/indicator in the scenario-scoped nav, and the visible focus ring on interactive elements. Not used for status text, table rows, or decorative elements.

Destructive is declared for design-system consistency across the milestone but **has no surface in Phase 1** — there is no delete/destroy affordance anywhere in this phase (scenarios are not deletable in v0.4). Phases 2-4 will consume this token first.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | "New Scenario" (button, top-right of the Home page header; opens the create modal) |

## UI Considerations

> Populated by the ui-phase UI-consideration probe (Step 9.5). Shape-rooted UI *state* coverage (empty / loading / error / populated / partial / overflow / zero-one-many / long-text). Empty-state and error-state COPY live in `## Copywriting Contract` above — this section covers state coverage and references those rows.

Applicable state considerations resolved: 9 covered, 2 backstop, 0 unresolved.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | Scenario list (0 scenarios) | ✅ covered | Renders the "No scenarios yet" empty state (see Copywriting Contract) with the same "New Scenario" CTA — no blank div, ever. |
| loading | Scenario list initial fetch | ✅ covered | Centered spinner + "Loading scenarios…" text while `GET /scenarios` is in flight. No skeleton rows — avoids flashing fake content before real data exists. |
| loading | Create-scenario submit | ✅ covered | "Create" button shows a spinner and is disabled for the duration of `POST /scenarios`; the Select and name input are also disabled to prevent a second submit. |
| error | Backend unreachable (network error on any fetch) | ✅ covered | Persistent inline banner at the top of the page content (see Copywriting Contract) — not a toast, because the condition persists until the backend starts and must stay visible, not auto-dismiss. |
| error | `POST /scenarios` → `400` unknown fixture | ✅ covered | Inline error under the fixture Select inside the still-open modal — user's in-progress input (name) is not lost. |
| error | `POST /scenarios` → `422` empty name | ✅ covered | Client-side check blocks submit before the request fires; inline error under the name field. |
| error | Render-time exception anywhere in the tree | ✅ covered | A top-level React error boundary renders the crash-backstop full-page message — last resort, not the primary error path. |
| zero-one-many | Fixture picker options from `GET /fixtures` | ✅ covered | Zero fixtures: Select renders disabled with placeholder "No fixtures available" and the Create button is disabled. One or many: normal Select behavior, no special-casing. |
| zero-one-many | Scenario list row count | ✅ covered | 1 row renders identically to the populated-many case; no pagination in v0.4 — list scrolls within a fixed-height container past roughly 10 rows (portfolio-scale data, not a shipped multi-tenant product). |
| long-text | Scenario name, fixture filename in the table | 🧪 backstop | Both truncate with ellipsis + a native `title` tooltip on hover; fixture filename renders in a monospace font to read as a file identifier. Name has no server-side max length (`ScenarioCreate.name` is just non-empty), so this is a held-out visual check at execution, not a hard-coded truncation width verified here. |
| overflow | Create-scenario modal on a very long fixture list | 🧪 backstop | Select's own internal scroll (Radix `Select` default) is assumed sufficient; not verified against an actual long fixture list in this spec — held out as a backstop for execution/QA. |

**Note on CORS/network-error honesty:** browser `fetch` cannot reliably distinguish a CORS-blocked request from a server that is simply not running — both surface as a generic network error. The "Can't reach the ShiftMind API" copy is deliberately non-diagnostic rather than falsely claiming to know *which* of the two failed; over-claiming here would itself be a dishonest surface.
